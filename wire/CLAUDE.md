# Wire Layer (wire/ — k2v5 composite protocol)

~330 test functions. QUIC/H3 primary, TCP-WS/smux fallback.

## Interfaces (wire.go)

```go
// Client transport (L4 proxy model)
type Dialer interface {
    DialTCP(ctx context.Context, addr string, earlyData []byte) (net.Conn, error)
    DialUDP(ctx context.Context, addr string) (net.PacketConn, error)
    // DialStreamUDP opens a stream-backed UDP session (reliable, congestion-controlled).
    DialStreamUDP(ctx context.Context, addr string) (net.PacketConn, error)
    // Reset clears cached connection state without closing the Dialer.
    Reset()
    Close() error
}

// Server transport
type Listener interface {
    AcceptTCP(ctx context.Context) (conn net.Conn, addr string, err error)
    ServeUDP(ctx context.Context, handler UDPHandler) error
    Close() error
}

type UDPHandler interface {
    HandleUDP(conn net.PacketConn, addr string)
}

// Optional — type-asserted on Dialer, not part of Dialer interface
type StatsProvider interface {
    WireStats() WireStats
}
```

## Config (wire.go)

`Config` parsed from `k2v5://udid:token@host:port?ech=...&pin=...&fp=...`

Fields: UDID, Token, Host, Port, ECH, Fingerprint, Insecure, Pin.

**`Fingerprint` (`fp=`) shapes the TCP-WS leg only.** It picks a uTLS
`ClientHelloID` for `tcpws.go`. The QUIC leg does not read it: it always sends
Chrome-146-over-QUIC — `buildChromeH3Spec()` for the ClientHello and
`chromeH3InitialPacketSpec()` for the Initial *packet* around it
(`quic_fingerprint.go`) — because Chrome's HTTP/3 ClientHello is not the same
shape as its TCP one and there is exactly one QUIC parrot to choose from. Adding
an `fp=` value that only exists on one leg would leave the other leg silently
unshaped — the state this replaced.

Port hopping was removed at the protocol layer: the dial port is whatever the URL
says (443 in production) and never moves. A legacy `hop=` emitted by an
un-upgraded server parses clean and is dropped — never resurrect it as a
dial-port override, a random high UDP port is exactly the anomaly the 443
camouflage exists to avoid.

## Files

- `wire.go` — Dialer/Listener/UDPHandler interfaces, `WireStats`/`StatsProvider`, Config, `ParseURL()`. `WireStats.CC` is the client's **uplink** sender's cumulative `k2cc.CCSummary` (zero, `SenderID=0`, on tcpws / before connect) — diff with `Sub` to read a window; the download direction is only in the server's cc-summary line.
- `auth.go` — `AuthVerdict` (OK 通过 / no-opinion 无意见 / explicit reject 明确拒绝 401-403 / cannot-determine 无法判定 -1 / node-fault 节点自身故障 -2) + `Validator` — the single device-auth abstraction for BOTH transports. **-2 is not -1 and not 401**: it means THIS node cannot authenticate anyone (no `K2_NODE_SECRET`, unresolvable node IPv4). It outranks -1 at the chain tail (permanent, not transient) and surfaces to the client as a **5xx server** code, so one misconfigured node never tells every device that ITS credentials are bad — and the client keeps racing to a healthy node instead of giving up on a 4xx. Auth rides the metadata stream (StreamType 0x10), validated by `handleMetadataStream` in `quic.go`/`tcpws.go`. Validators: `auth_users.go` (`NewUsersFileValidator`, `ChainValidators` — four-state chain semantics: no-opinion is skipped and the chain keeps going, -1 is remembered but the chain keeps going, an explicit 401/402/403 short-circuits immediately; the tail returns -1 if any validator saw "cannot determine" and none explicitly rejected, else fail-closes to 401), `auth_remote.go` (`NewRemoteValidator` → Center `POST /slave/device-check-auth` with `Basic ipv4:NodeSecret`), `auth_cache.go` (`CachingValidator` — caches OK verdicts only, singleflight-deduped concurrent lookups, TTL default 15m). **The old ticket flow (spec §4 `POST /k2v5/auth` + `TicketStore`) was never wired end-to-end and was removed 2026-07 — do not reintroduce it.**

Channel choice is owned by a hysteresis FSM (`selectorState`/`selectorStep`, pure — no I/O/time.Now/logging) driven by `evaluateSelector`, called after every `DialTCP`/`DialUDP`/`DialStreamUDP`/`Handshake` AND once per `engine/health.go` echo-probe tick. `selState.active` is the **only** source of truth for which channel serves traffic; `ActiveChannel()`/`FallbackActive()` (now a thin `ActiveChannel()=="tcpws"` derivation) read it — there is no separate `fallbackActive` bool anymore. Concrete types have NOT disappeared from the selection path, though: `evaluateSelector` still asserts `tm.primary.(*QUICClient)` to read `ConsecConnFails()` for the fast path, and `TCPRecentlyHealthy` asserts it to read the QUIC-side TCP-success clock. What the FSM itself consumes is the `primaryChannel` label (`channelForType(primaryType)`, `"quic"`/`"tcpws"`) — that is the abstraction the topology gate below is built on.
  - **Switch away (QUIC→TCP-WS)** is score-driven, asymmetric hysteresis: two independent triggers, either one fires it. Fast path — `consecConnFails >= 3` (genuine handshake failure, UDP blocked), same threshold as before, no exponential backoff. Quality path — `scoreTCPWS > scoreQUIC × 1.5` (`switchAwayRatio`) held continuously for `qualitySustainWindow` (10s) AND `backupFresh >= backupFreshSamplesGate` (2) AND `scoreTCPWS >= minSwitchTargetScore` (0.3). `backupFresh` is `ChannelScore.FreshSamples(now)`: tcpws availability samples inside the score's own staleness window (`scoreStaleMult × probeInterval`) — **windowed, not since-Reset** (it used to be a monotonic counter, which on a long-lived mobile process kept the gate satisfied with hours-old samples). The 0.3 floor is the positive-evidence rule: the target must be measured strictly better than "unknown" (neutral² = 0.25; two failed echoes also land below it). Without it the ratio degenerates once QUIC collapses toward 0 (loss ≥ 0.5 zeroes `QualityFromLossRTT`), and any positive tcpws score would "win" — the floor gates the switch only, never the sustain clock. Each switch-away sets the rollback review window (`switchAway()`) from two schedules: the base flap-damping doubling `flapWindowBase` (30s) `<< flapCount`, capped at `flapWindowMax` (600s), and on top of it the **rollback-trial escalation** — a rollback to QUIC is a trial, and a switch-away inside `rollbackTrialWindow` (120s) of the last return to quic (`selState.rollbackAt`, stamped by the echo-verified rollback and by `ReplacePrimary` when tcpws was serving) grades it failed: `failedTrials` 1 → the window is `flapWindowMax` outright, ≥2 → `stickyReviewWindow` (1h, a TTL so a session outliving the carrier's QoS episode still goes home); a switch-away later than that resets `failedTrials` to 0. Without it an echo-passing, bulk-dropping path oscillates on the base ramp alone — every window ends in a rollback that fails under load ~30s later (a ~25s outage per rung), and a re-race or wake restarted the ramp at 30s. Pinned by `TestSelector_FailedTrialEscalatesReviewWindow` / `TestEvaluateSelector_FailedTrialsEscalateToSticky`. **The quality path is not a corner case**: a carrier that QoS-drops bulk UDP while TCP flows clean passes the QUIC handshake and small echoes and still delivers nothing (ticket #3747, Android) — "QUIC beats TCP-WS at any loss rate" is not a safe assumption; the scoreboard measures.
  - **Topology gate (whole quic branch)**: `selectorStep` returns `channelStay` outright when `in.primaryChannel == "tcpws"`. When TCP-WS wins the startup race outright, `setupOutboundTransport` installs the SAME dialer as `tm.primary` and `tm.tcpws` while `selState.active` still holds its `"quic"` default (a re-race landing on tcpws produces the same shape). Every measurement then lands on `scoreTCPWS` (~1.0) while `scoreQUIC` has no source and sits at the neutral floor 0.25, so the quality path's ratio holds forever and the FSM would "switch away" from a QUIC channel that does not exist — a fabricated `reason=quic-quality-degraded`, `FallbackActive` flipped, and `runProbeOnce` engaged against a TCP-WS primary. Pinned by `TestSelector_TCPWSWonOutright_NoPhantomSwitchNoQuicRecovered`.
  - **Switch back (TCP-WS→QUIC) is echo-gated ONLY — deliberately no score comparison.** While tcpws serves traffic, QUIC carries none, so its quality is unmeasurable and `scoreQUIC` sits pinned at neutral; a `scoreQUIC > scoreTCPWS × k` gate would be mathematically unreachable against a healthy tcpws and would strand users on the stateful fallback forever (see `selectorStep`'s doc comment, spec §3.2). The sole gate is `quicEchoRecovered` — set by the background probe (`runProbeOnce`, 30s interval, active only while fallback is active) after a **fresh QUIC handshake AND 3 consecutive echo rounds** via `EchoProber.RunEchoProbe` both pass; a bare handshake success is never enough (root cause A: the old probe cleared fallback right after the handshake alone). The flag is one-shot: `evaluateSelector` consumes it (`Store(false)`) the moment it actually switches back, so a later re-fallback must re-earn it. Anti-thrash is that 3-round echo proof plus `nextReviewAt` (the flap window above) — not scores.
    - `runProbeOnce` runs **only when the primary is the quic channel** (`channelForType(PrimaryType())=="quic"`, checked right after the `FallbackActive()` gate). Everything it does — recording under the hardcoded `"quic"` channel, arming `quicEchoRecovered` — is meaningless against a TCP-WS primary and would double-probe the connection `engine`'s own `echoProbeLoop` is already probing.
    - It also re-checks `FallbackActive()` immediately before storing the result: it spends ~20s in unlocked I/O, and a rollback landing mid-probe would otherwise be re-armed with the finished episode's evidence, letting the NEXT fallback roll back with no fresh verification (the exact invariant this machinery exists for). Stale result → dropped.
  - Per-request fallback (unchanged): `DialTCP`/`DialUDP`/`DialStreamUDP` still try the primary first and fall back to TCP-WS on a single failed dial, independent of the channel-selector FSM's steady-state choice — a transient primary dial failure doesn't have to wait for the FSM to catch up.
  - Two dual-channel `ChannelScore`s (`scoreQUIC`/`scoreTCPWS`, `[0,1]`, staleness-gated to neutral 0.5) are fed by: `RecordQUICStats` (QUIC's congestion-control loss/RTT, from `WireStats()`, sampled 1Hz for **every** outbound by `engine/health.go`'s `sample()` — not just the primary/active one, so a non-primary outbound's score never goes stale and false-trips the quality path) and `RecordEchoResult`/`RecordAvailability` (echo-probe outcomes on whichever channel was actually probed — see `engine/CLAUDE.md` health.go section for the primary/backup probe split and cadence).
  - **Data-path fast path (round 3, #3757)**: a third switch-away trigger, `selectorInput.dataPathDistressed` — within the last `dataPathWindow` (60s), ≥ `quicRespTimeoutThreshold` (3) primary-channel `DialTCP`s on quic were sent and never answered (`ProxyLayerError.ResponseTimeout`, produced only by `readResponseError` at both transports' `ReadStreamResponse` deadline) AND those are ≥ 1/`dataPathTimeoutShare` (a third) of the window's quic requests. A `StreamError`/rejection is *answered* (a status arrived) and counts on the other side of the share; an EOF/connection error on the response read (`Unanswered` but not a timeout) and a transport-layer failure are not events at all (a reset would otherwise fake a burst of timeouts). **A share, not a consecutive streak**: the carrier shape is mixed — a fresh per-flow token bucket lets each new connection's first requests through, and each same-path re-race hands out a new one, so "three in a row" was unreachable in emulation while a third of everything died (#3757's heartbeats: `dialOk=2 dialFail=1`). Gated like the quality path on `backupFresh ≥ 2` and `scoreTCPWS ≥ minSwitchTargetScore`, but with no sustain window and **no loss term**: this is the one signature a carrier that drops bulk UDP but passes handshakes and echoes is guaranteed to leave, and CC loss is not — an app-limited sender completes no monitor interval, so `loss` reads 0.000 for minutes while requests die at the 5s deadline (#3757: 205/260 QUIC heartbeats at loss 0; the emulated per-flow-policed link took 32s of dead dials to reach critical). The window lives in `TransportManager.dpRing` (`recordQUICDataPath`, called from `DialTCP`'s primary branch when the primary is the quic channel) and is **path-scoped** like the scores: `ResetConnections`, a wake and a re-race from quic keep it (the 60s window expires it on its own); `Reset`, the rollback that starts a trial and `ReplacePrimary` from a serving tcpws clear it (a trial must run on its own evidence, else fresh tcpws samples re-fire the path before QUIC carried a request). Exported as `DataPathDistressed(now)` for `engine/health.go`'s backup-probe gate. Accepted trade: a node whose egress is dead for every destination (#3463) produces the same timeouts and lands on tcpws to the same node — a channel choice, not an outage, undone by the trial machinery once requests are answered. `recordDialOutcome` still ignores proxy-layer errors entirely (availability unchanged). Pinned by `TestDataPathDistressed_Predicate` / `TestSelector_DataPathTimeoutFastPath` / `TestTransportManager_DataPathDistressWindow`.
  - **Trial grading is by traffic, not wall clock** (round 3): `recordQUICDataPath` stamps `selectorState.firstAnsweredAt` on the first server-answered quic dial after a return to quic, and sets `trialProven` on an answered dial `rollbackTrialWindow` or more after that — answered requests across a window of *use*, not one answered burst (a fresh per-flow token bucket hands the first few requests through for free; #3757's log answered ~6 dials after every reconnect and then died). Both cleared by the rollback / by `ReplacePrimary` from a serving tcpws. `switchAway` grades a trial failed when the switch-away is inside `rollbackTrialWindow` **or** the trial was never proven — a user who rolled back, sat idle for ten minutes and then failed on the first taps gets the same escalation as one who failed 20s in; only a stay that kept answering across the window resets `failedTrials`. Pinned by `TestSelector_UnprovenTrialGradesFailed` / `TestTransportManager_TrialProvenByAnsweredDial`.
  - Observability: `evaluateSelector` logs `DIAG: transport-switch` (reasons `quic-quality-degraded`/`quic-handshake-threshold`/`quic-datapath-timeout` on switch-away, `quic-recovered` on switch-back, plus the legacy `SetFallbackActiveWithReason` reason `quic-race-lost` when tcpws wins the initial transport race and QUIC is installed as primary with fallback already active), `DIAG: quic-datapath-timeout` once per rising edge of the distress predicate (`dataPathEdgeLocked`, evaluated at record time and at every selector evaluation), and `DIAG: channel-review` (a rate-limited rollback-review status snapshot — see root `CLAUDE.md`'s DIAG event table for all three).

Clearing the min-RTT ratchet is the load-bearing one: unlike the EWMAs it never decays on its own, so a 5 ms LAN baseline carried into an 80 ms mobile path pins `QualityFromEchoRTT` at ~0.06 and silently disables the quality path for the process lifetime.

Pinned by `TestResetConnections_PreservesScoreboard`.

## ECH Rotation Flow

1. `EnsureECHPrivateKey(keyPath)` — load or generate X25519 HPKE key (auto-migrates old format)
2. `ECHProvider.FetchTemplate()` → Cloudflare DNS HTTPS record → extract config_id, cipher_suites, public_name
3. `GenerateECHKeyFromTemplate(tmpl, privKey)` → forged config (config_id = Cloudflare's + 1)
4. `SaveECHConfig(dir, config)` / `LoadAllECHConfigs(dir)` → multi-config storage (sorted by config_id desc)
5. `BuildECHKeys(privKey, configs)` → `[]tls.EncryptedClientHelloKey` for TLS config

## Client TLS Verification Priority

1. `pin=sha256:...` → InsecureSkipVerify + pin hash check (most secure)
2. `insecure=1` → InsecureSkipVerify (dev/testing only)
3. Default → system CA + Kaitu CA - Chinese CA blocklist (CNNIC, WoSign, WoTrus, CFCA, GDCA, SHECA)

## Gotchas

- `EchoProbe` verifies Short Header data path — QUIC handshake success (Long Header) does NOT prove data can flow. Middleboxes can allow Long Header but drop Short Header packets. Always echo-verify QUIC before declaring it the winner.
- `echo-probe-unsupported` backward compat: `IsEchoUnsupported(err)` returns true for all non-timeout errors (stream reset/EOF = old server, which hits `QUICServer.handleStream`'s `default:` → `stream.Close()` → client reads EOF). All three consumers share this one predicate — `race.go` (unsupported still wins the race), `probe.go` (short-circuits to `EchoSupported=false`, `Score()` sentinel `-1`), and `engine/health.go` `echoStep` (unsupported grows trust, never strikes). So a misclassification here blinds transport selection, node scoring, and re-race simultaneously.
- **A timeout is not `context.DeadlineExceeded`.** `EchoProbe` arms its response read with `stream.SetReadDeadline`, and quic-go answers an expired stream deadline with its own `deadlineError` — it unwraps to `os.ErrDeadlineExceeded` and reports `net.Error.Timeout()`, but **never** matches `context.DeadlineExceeded`. `IsEchoUnsupported` originally tested only the latter, so a black-holed data path (handshake passes, Short Header dropped — exactly what echo exists to catch) read as "old server, no echo support": trust grew, strikes stayed 0, no re-race, no TCP-WS fallback, and the UI kept showing connected while nothing loaded. Ticket #3463. Because the predicate's default is fail-open, a missed failure mode is silent — over-match timeouts here. Regression cover: `TestIsEchoUnsupported_RealStreamDeadlineIsNotUnsupported` drives a real quic-go connection to a real read deadline; every other echo test feeds a synthetic error and is blind to this class of bug.
- `RaceTransport` creates independent QUICClient instances per candidate. Loser cleanup is async via WaitGroup + safego.Go. Winner is returned immediately.
- Metadata response is `[0x00][MetadataFrame kv]` — `0x02` is taken by coded errors, success-with-payload rides behind `0x00`. Old clients read one status byte and `Close()`; leftover kv bytes are discarded safely on both transports (`TestMetadataResponse_OldClientSafe_*`). Server metadata streams must `CancelRead` on QUIC or the stream slot leaks.
- Device attribution (`ctx.dev.set` in QUIC's `handleMetadataStream`, bare `dev.set` in TCP-WS's) is gated on `verdict.OK`, independent of the enforce/permissive admission gate — a self-reported udid without a passing verdict is never trusted for accounting and lands in the empty-udid bucket even in permissive mode. Positive-attribution coverage: `TestQUICMetadata_AttributionSetOnOK` / `TestTCPWSMetadata_AttributionSetOnOK`; negative: `Test{QUIC,TCPWS}Metadata_AttributionRequiresVerdict` (`metadata_server_test.go`).
- `quicStreamConn.Close()` must call both `CancelRead(0)` and `Stream.Close()`. quic-go's `Stream.Close()` only closes the write direction (FIN). Without `CancelRead`, the receive half never completes and the stream slot leaks — causing `OpenStreamSync` to block at `MAX_STREAMS`. Fixed in the custom `Close()` method.
- `ReadStreamHeader`/`ReadStreamResponse` need `io.ByteReader` — wrap conn with `bufio.NewReader(conn)`.
- `net.Pipe()` is synchronous — structure goroutines carefully in tests.
- ECH base64 in URLs must use `base64.URLEncoding` (standard `+` corrupted by `url.Query()`).
- Outer SNI = ECH config's `public_name` because the current client emit sets it (`metacubex/utls handshake_client.go:310`, `u_handshake_client.go:474`); k2 adds no `SetSNI` override. **Not a hard rule** — the metacubex server does not enforce outer-SNI == `public_name` (`ech.go:610`), so it can be decoupled by overriding the emit. Decoupling collides with server-side camouflage (`server.learnOuterSNI` trusts only the node's own `public_name`) — see `docs/superpowers/specs/2026-08-10-outer-sni-camouflage-design.md`.
- **Inner SNI is readable BEFORE the server sends its certificate — reading it does NOT require completing (terminating) the TLS handshake.** The server HPKE-decrypts the ECH extension while *processing* the ClientHello: `metacubex/utls handshake_server.go:44` calls `readClientHello` first thing, which at `:152-157` runs `processECHClientHello` (swaps in the decrypted inner hello) *before any other negotiation*; the `GetConfigForClient` (`:161`) and `getCertificate` (`:266`) callbacks then receive the **decrypted inner** `ClientHelloInfo`, and both fire before ServerHello/Certificate go out. So a server can gate on the inner SNI (ECH-encrypted, invisible to a passive observer) and bail/relay *without ever exposing its self-signed cert*. **k2 currently reads the inner SNI LATE** — `server/server.go:823` reads `ConnectionState().ServerName` after `Handshake()` returns (cert already sent). That is an implementation choice, not a protocol limit — worth knowing if you ever need to decide *before* presenting the cert.
- **The self-signed cert IS active-probe-reachable via a forged ECH extension — routing was on ECH *presence*, not decryptability.** `handleRawTCP` routed any `HasECH` ClientHello to `handleK2V5`, which called `tls.Server(...).Handshake()` unconditionally. When ECH decryption fails, utls proceeds with the OUTER hello (`ech.go:630` `return outer, nil, nil`) and `getCertificate` (`server.go:430`) hands back the self-signed cert unconditionally, so the handshake **completes and exposes the self-signed cert** — a config-free de-anon: a censor (or Chrome's default GREASE ECH) sends a syntactically-present but undecryptable ECH ext, completes TLS with its own key share, and reads the self-signed cert. This contradicted spec §3.7 ("decrypt-fail → reverse-proxy"). **Fixed** by the config_id gate: `server.handleRawTCP`/`echDisposition` reads the plaintext outer `config_id` (offset 5 of the ECH ext — verified against utls `parseECHExt`) and routes any config_id the node does not own (`ownsECHConfigID`) to `ReverseProxyWithTimeout(..., camouflageName+":443", ...)` **before** any TLS state. **Residual**: config_id is plaintext on the wire, so a prober who replays a real config_id it observed still reaches `handleK2V5`, fails decryption, and completes the handshake — fully closing that needs out-of-band HPKE decrypt, which metacubex/utls keeps in `internal/hpke` (blocked without a fork/new dep). The earlier "config-holder de-anon is a phantom" reasoning still holds for the *config-holder* vector (holders are already users; TLS 1.3 ECDHE defeats replay-for-cert), but it does NOT cover this forged-ECH vector. Design/rationale: `docs/superpowers/specs/2026-08-10-outer-sni-camouflage-design.md`.
- QUIC connection liveness: quic-go's KeepAlive (10s) + MaxIdleTimeout (30s) detect dead connections at protocol level. `conn.Context().Done()` fires when connection dies. `connect()` checks this before reusing cached conn — no manual `resetConnection()` needed on error paths. macOS sleep/wake is handled by singTunMonitor → `OnNetworkChanged()` → `Reset()` (desktop), or by platform-native callbacks (appext). No application-level wall-clock staleness check needed.
- Stream response timeout ≠ transport failure: A 5s stream response timeout means the server's upstream `net.Dial` to the destination is slow/failing — NOT that QUIC transport is broken (OpenStreamSync succeeded = transport is alive). Do NOT increment `handshakeFailStreak` or trigger TCP-WS fallback on stream timeouts. `handshakeFailStreak` is strictly for QUIC handshake failures (UDP blocked by firewall).
- Proxy-layer errors skip TCP-WS fallback: Dialer marks errors as proxy-layer after the request is sent (stream opened + header written). `ProxyLayerError` wrapper and `StreamError` both implement `IsProxyLayer() bool`. `TransportManager` checks via interface (`proxyLayerErr`), not type enumeration. Covers: `StreamError` (server error code), `ErrStreamRejected` (server rejection), `ReadStreamResponse` timeout (server processing). Only transport-layer errors (handshake failure, stream open failure, write failure) trigger per-request fallback.
- Relay UDP unhealthy → `ErrDatagramRelayUnhealthy`: When relay datagram path has consecutive relay timeouts (threshold: 3), `DialUDP` returns `ErrDatagramRelayUnhealthy` for per-request TCP-WS fallback. A relay timeout is a `quicUDPConn` read deadline on a session that **sent and never received** (`txPackets > 0 && rxPackets == 0`), or a send the datagram budget shed (`maxDatagramInflight`). A session that was answered and then hit its idle deadline is not one: every UDP session ends on that deadline, and whenever the client had the last word (QUIC close, final ACK) the downlink deadline fires first — counting those marked a healthy path unhealthy after three quiet sessions. Loss rate tracking was removed (DNS racing inflated false positives). Any successful recv clears the timeout streak, and nothing else does — so an unhealthy relay keeps one way open for a datagram to arrive: `admitSession` lets **one new session per `relayTrialInterval` (30 s)** use the datagram path anyway (INFO `datagram relay unhealthy, trial session`). Its reply heals the relay (`datagram relay path healthy again`); if it goes unanswered, that one flow is black-holed until its idle deadline (up to 60 s, so two unanswered trials can be open at once) and the next trial is an interval later — healing therefore waits for a trial that lands on a destination which answers. DNS is never the trial (it uses `DialStreamUDP`), and no trial happens while the active channel is TCP-WS (`TransportManager` does not ask QUIC then). Without the trial, once the last datagram session had ended nothing could arrive any more and the relay stayed unhealthy until the QUIC connection was replaced — on a router, as long as it ran (three LAN broadcasts to nobody were enough to get there). The schedule is set when the relay is marked unhealthy and is not pushed out by later timeouts (shed bursts, the trial's own). The clock is monotonic (`relayEpoch`). Relay-layer metrics never trigger wire-layer actions (reconnect, transport switch). See `VOCABULARY.md`.
- QUIC flow control is platform-specific (build tags `ios || android` vs desktop) — mobile uses smaller windows (2 MB stream / 8 MB conn vs 8 MB / 20 MB desktop) to stay under iOS NE jetsam limit.
- QUIC stream responses have 5s timeout to prevent indefinite blocking on slow/dead servers.
- `DialTCP(ctx, addr, earlyData)` sends earlyData after stream header, before reading server response. Server's `bufio.Reader` naturally buffers it during header parsing; `pipe()` consumes it after upstream dial. Saves 1 RTT on high-latency links. Backward compatible — old servers handle it without changes. Pass `nil` for no early data.
- `SendDatagram` uses atomic inflight counter (`maxDatagramInflight=8`, `wire/quic.go:55`, `ErrDatagramSendTimeout`) — quic-go's own datagram queue holds up to 32 frames and blocks indefinitely (`datagramQueue.Add()`) once full under congestion. Our cap must stay well below that 32: with N sessions sharing one queue, only `maxDatagramInflight` goroutines are allowed into the blocking `Add()` path at once, so a value close to 32 would let most `HandleUDP` goroutines pile up there together instead of continuing to read from their targets. When concurrent SendDatagram calls exceed the limit, excess packets are dropped immediately (protocol-correct for unreliable DATAGRAM). No goroutine spawned — avoids leak when SendDatagram blocks. Applies to both client `quicUDPConn.WriteTo` (via `quicUDPMux.sendInflight`) and server `serverUDPConn.WriteTo` (via `connUDPState.sendInflight`).
- UDP sessions are multi-destination: one session (= one client source port) can address many destinations over its lifetime. Uplink `UDPFrame.Addr` is **that packet's** destination; empty means "same as the session's first destination". Downlink `UDPFrame.Addr` is the **actual source** the reply came from; empty means "from the session's first destination" (old server, pre-multi-dest). Both ends fall back to the session's first destination on an empty addr, so the *frame encoding* interoperates in any old/new combination. See `udp.go` (`UDPFrame`) and `server/handler.go` (`HandleUDP`'s per-session destination LRU, `maxUDPDestsPerSession = 64`).
- **The empty-addr fallback returns the session target VERBATIM, which may be a hostname** — `DialUDP(ctx, dest)` stores `dest` unparsed in `targetAddr`, and `core/tunnel.go handleUDP` hands it a *domain* whenever the QUIC SNI upgrade or the IPv6→hostname rewrite fires. So a new client talking to a not-yet-upgraded node gets a hostname `net.Addr` out of every `ReadFrom`. Callers must not assume it is an IP: sing-tun rejects a non-IP write destination with `os.ErrInvalid`, which used to kill the whole session on the first downlink packet. `core.pipePacket` now repairs it (`repairSourceAddr` → the session's primary destination) rather than the wire layer re-resolving per packet. Do not "simplify" that back into a `ResolveUDPAddr` here: it puts DNS on the per-packet hot path and can hand the app an IP it never addressed, which its connected socket then discards. So the honest interop claim is: **wire-level frames interoperate in any combination; the hostname-shaped fallback address is a real hazard for anything that writes it to a socket.**
- **UDP drop instrumentation — what a `0` means, per transport.** Every path that silently discards a UDP packet increments a counter, so `0` never means "nobody counted":

  | path | `UDPTxDrops` | `UDPRxDrops` (live session, channel full) | `UDPRxDropsNoSession` |
  |---|---|---|---|
  | QUIC datagram (`quicUDPMux`) | send budget saturated | ✅ | ✅ |
  | QUIC stream-UDP (`quicStreamUDPMux`) | n/a — always 0 | ✅ | ✅ |
  | TCP-WS smux (`smuxUDPMux`) | n/a — always 0 | ✅ | ✅ |

  The two `n/a` cells are **not gaps**: a stream-backed transport has no lossy send path — `writeFrame` either writes the frame or returns an error to the caller, so a lost packet is always an explicit error, never a silent discard. But note what that error does **not** do: it kills only the *mux* (that one relay stream), never the smux session or QUIC connection carrying it. The session stays up, `DIAG: heartbeat` keeps reporting `healthy`, and only UDP is affected. Until #3420 that was an outright trap — the dead mux stayed cached and every later UDP send failed instantly; now the next dial evicts and rebuilds it, which you see as `DIAG: udp-mux-rebuild`. So a UDP-only outage with a healthy heartbeat is a real shape: read `udp-mux-rebuild`, not the drop counters. Only the datagram path can accept a packet from the app and then silently discard it. `WireStats.Transport` + `WireFallback` tell you which row you are reading. `UDPRxDropsNoSession` is deliberately **not** folded into `UDPRxDrops`: it is dominated by the benign tail of packets arriving just after a session closed or was idle-reaped, so it scales with session churn, not with loss — a rising `udpRxDrops` is a stuttering user, a rising `udpRxDropsNoSess` usually is not. All counters are cumulative for the life of the connection; diff two heartbeat samples to read a rate.
- `InitialPacketSize = 1400` (not quic-go default 1280): QUIC DATAGRAM frames must fit in a single packet. Browser QUIC Initial packets (1250 bytes payload) create UDPFrame of 1274 bytes. With default 1280, `currentMTUEstimate = 1243 < 1274` → `DatagramTooLargeError` → silent overflow stream fallback, defeating datagram relay's QUIC-over-QUIC design. 1400 gives estimate 1363, safe for all standard Ethernet paths (IPv4 packet = 1428 < 1500). PMTU discovery handles rare sub-1400 paths.
