# Tessera 协议规范（`k2t`）

**版本**：Draft v0.1
**日期**：2026-07-27
**状态**：设计草案，未实现，未定案

---

## 1. 为什么需要它

### 1.1 k2v5 伪装层的结构性缺陷

k2v5 用**"ClientHello 里有没有 ECH 扩展"**来判断一条连接是不是自己人（`server/server.go` `handleRawTCP` 检查 `info.HasECH`）。

**这是一个明文的、任何人都能观察和伪造的标志位。** 由此产生两个可直接利用的后果：

**后果一：一次连接即可证伪节点身份。** 探测者发送一个带 ECH 扩展、但 `config_id` 为垃圾值的 ClientHello：

1. `PeekClientHello` 看到 `0xfe0d` 扩展 → `HasECH = true`
2. 进入 `handleK2V5` → `tls.Server(conn, s.TLSConfig).Handshake()`
3. Go 的 TLS 栈找不到匹配的 ECH 密钥 → ECH 被拒，但**握手继续**（client-facing server 行为，回送 `retry_configs`）
4. 服务端出示自签名证书 → **探测者拿到一张给 `cloudflare-ech.com` 签发、CA 验证不通过的证书**

证书补多长都无济于事——问题不在长度，在签发者。

**后果二：最常见的良性流量反而触发暴露路径。** Chrome 在没有真实 ECH 配置时会发送 **GREASE ECH 扩展**。因此任何一个 Chrome 用户偶然访问节点的 443 端口，都会被判定为"自己人"、进入 `handleK2V5`、拿到自签名证书——而不是被伪装反代导向一个正常网站。伪装在最高频的场景下失效。

### 1.2 ECH 的伪装前提已经过期

k2v5 协议规范 §3.1 的核心假设是：

> Cloudflare uses a single `public_name` for all ECH-enabled sites, so all legitimate Cloudflare ECH traffic shares the same outer SNI — **our traffic blends in naturally**.

**2026-07-27 实测普查（78 个域名 × 3 个独立 resolver：1.1.1.1 / 8.8.8.8 / 9.9.9.9）：**

| 结果 | 数量 |
|---|---|
| DNS HTTPS 记录中发布 `ech=` 的域名 | **2** |
| 其中不同的 `public_name` 数量 | **1**（`cloudflare-ech.com`） |
| 观察到的 `config_id` 取值 | **1**（`128`） |
| 有 HTTPS 记录但**不含** `ech=` | 24（含 `cloudflare.com` 自身、`discord.com`、`digitalocean.com`、`hubspot.com` 等全部受测 Cloudflare 托管站） |
| 无 HTTPS 记录 | 52 |

仅存的两个是 `cloudflare-ech.com` 与 `crypto.cloudflare.com`（Cloudflare 的演示端点）。**Cloudflare 已对客户域名关闭 ECH。**

结论：

- **可供混入的 ECH 流量池已不存在。** 那句假设在写下时（Cloudflare 2023 年曾大范围启用 ECH）可能成立，今天不成立。
- **真正的指纹是 ECH 扩展本身，而非其中写了什么名字。** 线路上出现 `encrypted_client_hello` 已属极稀有事件。在此前提下调整 `public_name` 属于在已暴露的维度上做微调。
- **附带发现的具体不一致**：现实世界唯一在用的 `config_id` 是 `128`；生产节点实测为 `150 / 245 / 247`（`GenerateECHKeyFromTemplate` 伪造为 `tmpl.ConfigID + 1`，且各节点抓取模板的时刻不同）。`config_id` 是**明文上线**的，因此即使外层 SNI 写着 `cloudflare-ech.com`，`config_id` 也与当前真实值对不上。

### 1.3 因此

Tessera 不是对 k2v5 伪装层的修补，而是替换它的判别机制与探测应答机制。隧道层（stream 复用、设备认证、拥塞控制）全部保留。

## 2. 威胁模型

假定审查者具备以下能力：

| 能力 | 说明 |
|---|---|
| **T1 被动指纹** | 记录并分类 ClientHello（JA3/JA4：扩展集合与顺序、GREASE、cipher 顺序、ALPN、supported_groups）、SNI、证书长度 |
| **T2 被动流量分析** | 包长分布、时序、方向性、连接时长、并发模式 |
| **T3 主动探测** | 对可疑 IP:port 主动发起连接，构造任意输入，观察响应 |
| **T4 DNS 关联** | 查询任意域名的 A/AAAA/HTTPS 记录，比对 SNI 与目的 IP 的一致性、比对域名是否真的部署某项特性 |
| **T5 统计分类** | 对流量特征做 ML 分类，容忍一定误报率 |
| **T6 长期观察** | 跨时间关联同一 IP、同一客户端的行为模式 |

假定审查者**不具备**：破解 X25519 / AEAD、在端点上执行代码、获取节点私钥。

**关键判据**：任何具备"零误报"性质的检测规则都是致命的——审查者可以无代价地封禁。设计的目标是让所有可用规则都带有不可接受的误报率。

## 3. 设计原则

按重要性排序。后面的每一条设计决策都可以回溯到这里。

**P1. 判别必须靠秘密，不能靠标志。**
区分"自己人"与"探测者"的依据，必须是只有持私钥者才能产生、观察者既无法复现也无法证伪的密码学证明。协议标志位、扩展存在性、端口、包长——任何可观察量都不合格。

**P2. 主动探测必须无法证实。**
不存在任何输入能让节点暴露自己。探测者得到的响应必须真实到可以通过 CA 验证。这要求未认证路径的响应**来自真实站点本身**，而非我们的模仿。

**P3. 各层必须自洽。**
TLS 指纹 / SNI / 证书 / IP / DNS / 流量形状——六层中任何一层与"我们声称的身份"对不上，都会把"常见"变成"唯一"。审查者的标准手法正是：用常见特征过滤出候选集，再用那一处不一致精确定位。

**P4. 不依赖人群存在。**
任何"混入某类流量"的设计都必须回答：那类流量今天还有多少？谁在维持它？它消失时我们怎么知道？ECH 是活教训——假设过期了两年而无人察觉。**特征时效性必须被持续测量，而非一次性论证。**

## 4. 协议规范

### 4.1 术语

| 术语 | 含义 |
|---|---|
| **front** | 被借壳的真实网站，例如 `www.example-major-site.com`。必须真实存在、从节点可达、部署 TLS 1.3 |
| **node** | 运行 Tessera 的服务端（k2s） |
| **short_id** | 8 字节客户端组标识，用于多租户区分与吊销 |
| **认证路径** | 判别成功，进入 k2 隧道 |
| **借壳路径** | 判别失败，整条连接被透明转发给 front |

### 4.2 密钥材料

节点持有一对长期 X25519 密钥 `(S_priv, S_pub)`，随节点置备生成并持久化。

`S_pub`（32 字节）通过连接 URL 分发给客户端，与 `front` 域名、`short_id` 一同下发。**`S_priv` 永不离开节点。**

### 4.3 连接 URL

```
k2t://<host>:<port>?pbk=<base64url(S_pub)>&front=<front域名>&sid=<hex(short_id)>&ip=<拨号IP>
```

- `host` — 内层标识，任意值（沿用 k2v5 语义：证书不按域名校验）
- `front` — 外层 SNI 与借壳目标
- `ip` — 实际拨号地址；`host` 不做 DNS 解析（沿用 k2v5 的 `wire.Config.Host` 语义）

### 4.4 客户端：ClientHello 构造

客户端使用 uTLS 以**真实浏览器 ClientHelloSpec**（当前基线：Chrome）构造 ClientHello，SNI 设为 `front`，随后在序列化前改写两个字段：

**第一步 — key_share。**
生成临时 X25519 密钥对 `(C_priv, C_pub)`，将 `C_pub` 作为 TLS `key_share` 中 x25519 组的公钥。这是浏览器本来就会发送的字段，形态无异常。

**第二步 — 派生认证密钥。**

```
shared  = X25519(C_priv, S_pub)
authKey = HKDF-Expand(HKDF-Extract(SHA-256, salt = C_pub, IKM = shared),
                      info = "k2t/v1 auth", L = 44)
          → key   = authKey[0:32]     (AES-256-GCM 密钥)
          → nonce = authKey[32:44]    (12 字节)
```

`shared` 因 `C_priv` 为每连接临时生成而唯一，故 `key` 亦唯一；**因此确定性 nonce 是安全的**（不存在同密钥重用 nonce 的情形）。

**第三步 — 构造 session_id。**

明文（16 字节）：

| 字段 | 长度 | 说明 |
|---|---|---|
| `version` | 1 | 协议版本，v1 = `0x01` |
| `flags` | 1 | 保留，v1 置 0 |
| `timestamp` | 4 | Unix 时间，分钟精度（大端） |
| `short_id` | 8 | 客户端组标识 |
| `reserved` | 2 | 置 0 |

```
session_id = AES-256-GCM_Seal(key, nonce, plaintext = 上表16字节, aad = front域名的UTF-8字节)
           → 16 字节密文 + 16 字节 tag = 32 字节
```

TLS 1.3 的 `legacy_session_id` 恰为 32 字节且浏览器填随机值，**容量精确吻合，无需额外携带任何字节**。

`aad` 绑定 `front`，使得截获的 `session_id` 无法搬到伪装成其他站点的节点上重放。

**实现要点（均由 §12 的实测确定，不可凭直觉替换）：**

- `session_id` 在序列化后的 ClientHello 中位于偏移 **39**（handshake 头 4 + legacy_version 2 + random 32 + 长度字节 1），长度 32。
- 改写必须**同时**写 `HandshakeState.Hello.SessionId` 与 `HandshakeState.Hello.Raw[39:71]`，**原地等长覆盖**。不要触发重新序列化——原地覆盖可保证 ClientHello 其余字节完全不变，指纹零漂移。
- 用于 ECDH 的私钥取自 `HandshakeState.State13.KeyShareKeys.Ecdhe`。**不要读同结构的 `CurveID` 字段——实测其值恒为 `0x0000`（未填充），据此判断曲线会出错。**

### 4.5 服务端：判别

节点在 443 端口接受 TCP，`Peek` 出完整 ClientHello（复用现有 `wire.PeekClientHello` 基础设施），然后：

1. 提取 `legacy_session_id`。长度 ≠ 32 → **借壳路径**。
2. 提取 `key_share` 扩展中 **group == `0x001d`（X25519）** 的条目作为 `C_pub`。不存在 → **借壳路径**。

   > **必须按 group 精确选取，不能取第一个条目。** 实测的真实浏览器会并列发送多个 key_share：Chrome PQ 发 3 个（`0x001d` 32B、一个 GREASE group 1B、`0x6399` X25519MLKEM768 1216B），Firefox 发 `0x0017`(P-256, 65B) + `0x001d`，Safari 发 `0x001d` + GREASE。GREASE 的 group 值每个指纹/每条连接都不同，必须跳过而非枚举。
3. `shared = X25519(S_priv, C_pub)`，按 §4.4 同法派生 `key` / `nonce`。
4. `AEAD_Open(key, nonce, session_id, aad = 本节点的 front 域名)`。失败 → **借壳路径**。
5. 校验 `version` 已知；`timestamp` 在 ±`REPLAY_WINDOW`（默认 ±10 分钟）内；`short_id` 在本节点有效集合内。任一不满足 → **借壳路径**。
6. 校验 `session_id` 未在重放缓存中出现（LRU，容量与 `REPLAY_WINDOW` 匹配）。命中 → **借壳路径**。
7. 全部通过 → **认证路径**。

**判别结果对观察者不可见**：两条路径在 ClientHello 层面输入完全相同，差异仅存在于服务端的私钥运算结果。

### 4.6 借壳路径

节点与 `front:443` 建立 TCP 连接，将**原始 ClientHello 字节原封不动**转发过去，随后双向管道直至任一端关闭。

关键性质：

- 探测者收到的是 **front 的真实证书链**，CA 验证通过
- 探测者进行的任何后续交互（HTTP 请求、TLS 特性协商）得到的都是 front 的真实响应
- 节点不产生任何自己的 TLS 材料，**不存在可供比对的伪造痕迹**

要求：

- `front` 必须从节点网络可达；启动时探测一次，不可达则拒绝启动（**失败必须显式，不可静默退化**）
- 借壳连接受并发信号量限制（复用现有 `proxySem`），过载时直接关闭连接——与"服务器繁忙"无异
- 借壳连接的读写超时应与真实浏览过程相称（非 k2 隧道的长连接参数）

### 4.7 认证路径

节点自行完成 TLS 握手。客户端已通过 §4.4 完成认证，**不做 CA 校验**（不做域名匹配，不做签名链验证）。

证书的处理有两个变体：

**变体 A（v1 采用，实现简单）**
节点出示自签名证书，长度经 `tlspad` 补齐至 `front` 证书链的实测长度（复用现有 `ProbeTarget` + `GeneratePaddedCert`）。

TLS 1.3 中证书是加密传输的，观察者只能测量加密握手记录的**大小**。补长使该大小与 front 相称。

> **注意**：这意味着**证书补长机制在 Tessera 下仍然承重**，不应退役。它从"给伪造证书打补丁"变成"让认证路径的握手尺寸与借壳路径一致"。

**变体 B（目标形态）**
节点获取并缓存 front 的**真实证书链字节**，在认证路径中原样出示，用自己的密钥签署 `CertificateVerify`。客户端不验签。观察者看到的握手在字节层面与真实访问 front 无异。

变体 B 需要在客户端与服务端两侧修改 TLS 栈（服务端需绕过"证书与私钥必须匹配"的约束）。**列为目标形态而非 v1 范围。**

### 4.8 隧道层

认证路径的 TLS 建立后，其上承载的内容**完全复用 k2v5 现有实现**：

- WebSocket 升级至 `/k2v5/tunnel` 或直接 smux（沿用现状）
- stream 类型、metadata 设备认证（`0x10`）、准入门（`admissionPolicy`）
- k2cc 拥塞控制

**Tessera 只替换"如何建立一条不被识别的加密通道"，不触碰通道内的任何东西。**

## 5. 六层一致性清单

P3 要求逐层自洽。当前设计在各层的状态：

| 层 | 处理 | 状态 |
|---|---|---|
| **L1 TLS 指纹** | uTLS + 真实浏览器 spec，两条传输统一 | ⚠️ QUIC 路径当前用 Go 标准库构造 ClientHello（`wire/quic.go` 丢弃了 ClientHelloID）。审查者能解出 Initial，该 ClientHello 与 TCP 侧一样暴露。**能力已具备**——`utls.UQUICClient` 实测可产出含 GREASE 的 Chrome QUIC ClientHello；代价是 quic-go 直接驱动 `crypto/tls.QUICConn`，接入需给 fork 打补丁（§6.4） |
| **L2 外层 SNI** | front 的真实域名 | ✅ 自洽 |
| **L3 证书** | 变体 A 补长 / 变体 B 真证书 | ✅ 借壳路径完全真实；认证路径见 §4.7 |
| **L4 IP** | SNI 与目的 IP 不匹配 | ❌ **无解**（除非自建 CDN 或公开节点 IP，后者等于把节点列表交给审查者）。靠 P2「探测无法证实」兜底 |
| **L5 DNS** | 不需要我们发布任何记录 | ✅ front 自身的记录天然存在且真实 |
| **L6 流量形状** | 未处理 | ❌ **v1 已知缺口**。已实测轴的量级，但零假设取不到，见 §14 |

**L4 是本设计承认的残余风险。** 它无法在不暴露节点 IP 列表的前提下消除。设计的赌注是：审查者若仅凭"SNI 与 IP 不匹配"就封禁，会误伤大量 CDN、企业前置代理、灰度环境等合法场景。这个赌注需要持续验证（见 §9）。

## 6. QUIC

代码在 [`spike/quic_test.go`](spike/quic_test.go)，`go test ./docs/tessera/spike/` 可复现。

本节此前写着两条判断，实测后**两条都是错的**，而且错的方向相反。

### 6.1 判别载体：`session_id` 在 QUIC 上不存在

原文称"§4.4 的 `session_id` 机制本身仍然工作"。**不成立。**

RFC 9001 §8.4 禁止 QUIC 使用 TLS 中间盒兼容模式，`legacy_session_id` 必须为空。Go 标准库把这条规则直接写进了代码（`crypto/tls/handshake_client.go`：*"The session ID is not set for QUIC connections (see RFC 9001, Section 8.4)"*）。实测一次 QUIC ClientHello：**1466 字节，`legacy_session_id` 0 字节**；同一字段在 TCP 路径上是 32 字节。

因此在 QUIC 的该字段写 32 字节，不是隐蔽判别，**是全网独一份的信标**——审查者能从明文 DCID 推出 Initial 密钥、解出 ClientHello，看到一个所有其他客户端都留空的字段被填满了。§4.4 的载体在 QUIC 上必须换。

### 6.2 借壳转发：不是做不到，是比 TCP 更干净

原文称"QUIC 的连接 ID 与包保护绑定在端点上，无法把一条 QUIC 连接原样转交给 front"。**不成立。**

包保护确实绑定端点——但借壳根本不需要解包。TCP 路径必须先窥探 ClientHello、再拼接字节流；QUIC 路径是**逐数据报原样转发**：节点不终结、不解密、不重组，判定后就是一个 UDP NAT。

实测：一个未认证的 QUIC 客户端拨向节点，完成完整握手，拿到 **front 的证书**（`CN=front.invalid`）与 **front 的服务响应**，节点全程没有终结任何东西。

同时验证了朴素中继会翻车的那一档：front 强制地址校验并回 Retry（客户端随即换用新的 Destination Connection ID）——**借壳仍然完整**。前提是中继状态按 **4 元组**而非连接 ID 建立。

### 6.3 载体：Initial 包的 Token 字段

`session_id` 换成 QUIC Initial 的 **Token 字段**（RFC 9000 §17.2.2）。它明文、变长、语义上就是"服务端之前发给我的一串不透明字节"。

变长带来一个 TCP 侧没有的好处：token 可以**同时装下客户端临时公钥和 AEAD 输出**，服务端因而**完全不需要解密 Initial、不需要解析 ClientHello**——整个判别是一次 varint 解析、一次 X25519、一次 AEAD open。

```
token = C_pub(32) || AES-256-GCM_Seal(key, nonce, 凭据明文(16), aad = front 域名)
      = 32 + 16 + 16 = 64 字节
```

`key` / `nonce` 的派生与 §4.4 完全一致（`salt = C_pub`）。实测：合法凭据通过；换 front（aad 变化）失败；对着别的节点公钥生成的凭据失败；全零 token 失败。

**关键前提已实测**：front 收到一个自己无法解码的 token 时，必须按"没有 token"继续握手，否则被转发过去的过期/重放凭据会产生节点掩盖不了的失败。quic-go 服务端正是如此——源码注释写明 *"we just ignore them, and act as if there was no token on this packet at all"*，端到端复测确认握手正常完成。

### 6.4 实现代价与未决

| 项 | 状态 |
|---|---|
| quic-go 客户端无法设置任意 token | **需给 `github.com/apernet/quic-go`（已在用的 fork）打补丁**。`ClientToken` 的载荷字段未导出、无构造函数；已加断言测试，将来上游若补上构造函数会失败提醒 |
| **token 存在性本身是否是特征** | **未普查。** 真实客户端只在此前拿到过 NEW_TOKEN 时才带 token。首包即带 token 的比例、以及审查者能否判定"首次"，均未测量。这是继 ECH 普查之后**同一类**的问题，必须实测而非推理 |
| token 长度分布 | quic-go 自签的 NEW_TOKEN 实测 78 字节，Tessera 为 64 字节，同量级。真实浏览器的分布未普查 |
| **连接迁移会打断认证连接** | 中继按 4 元组建立；认证连接若因 NAT 重绑定换了源地址，新 4 元组的首包是短头包、无 token，会被判为借壳而转走。**修法：短头包按 DCID 查本地已签发的连接 ID，命中则走本地。此修法未实测**，属推理 |
| 时序旁路 | §13 的结论同样适用：借壳路径多一个到 front 的 RTT。缓解方案相同 |

> §6 不再是"最大缺口"。判别载体与借壳机制都已落地并实测，剩下的是**普查 token 的真实分布**与**连接迁移**这两项——前者是可观测性问题（§9 同一套流程），后者是有明确修法的实现细节。当前最大缺口转为 **§8.2 的流量形状**。

## 7. 与 k2v5 的关系与迁移

**Tessera 是新增传输类型，不替换、不修改 k2v5。**

| 阶段 | 内容 |
|---|---|
| 1 | 节点同时监听 k2v5（现状）与 Tessera。互不干扰 |
| 2 | Center 按客户端版本决定下发 `k2v5://` 或 `k2t://` tunnel URL |
| 3 | 新客户端优先 Tessera，失败回落 k2v5 |
| 4 | 新版本铺开至足够比例后，逐节点关闭 k2v5 传输 |

存量客户端**零感知、零改动**——它们从未收到 `k2t://` URL，行为与今日完全一致。向后兼容性由"新增而非修改"这一结构保证，不依赖迁移期的小心操作。

## 8. 安全分析

### 8.1 本设计消除的攻击

| 攻击 | 消除方式 |
|---|---|
| 主动探测证伪身份 | 任何未通过 §4.5 的输入都得到 front 的真实响应；不存在能让节点暴露自己的输入 |
| Chrome GREASE ECH 误判 | 判别不再依赖任何扩展的存在性 |
| ECH 扩展本身作为稀有信号 | 不发送 ECH |
| `config_id` 与真实世界不一致 | 无 ECH 配置，无 `config_id` |
| 自签名证书泄漏 | 借壳路径不产生我们的证书；认证路径的证书对观察者仅体现为长度 |
| 跨节点重放 `session_id` | AEAD 的 `aad` 绑定 front；`short_id` 绑定节点有效集合 |
| 同节点重放 | timestamp 窗口 + LRU 重放缓存 |

### 8.2 残余风险与已知攻击面

| 风险 | 说明 | 缓解 |
|---|---|---|
| **L4 SNI/IP 不匹配** | §5 已述，无解 | 靠 P2 兜底；持续测量误报率假设是否成立 |
| **L6 流量形状** | 认证路径承载的是 VPN 流量，其包长/时序分布与浏览 front 显著不同。**长期观察（T6）可据此分类** | 已测量并改写为设计约束，见 **§14**：零假设不可得，故只能按构造使分布重叠（front 按流量类别选 / 限制单连接体量），二者裁决与未决问题 4 并案 |
| **两条路径的时序差** | 认证路径本地完成握手；借壳路径需额外到 front 的 RTT。**已实测：未缓解时完全可分（见 §13）** | 按分布采样注入延迟 + 预热连接池。**v1 必须实现，规范见 §13.3** |
| **X25519 计算 DoS** | 每条入站连接触发一次 X25519（约 50µs 量级）。攻击者可低成本迫使节点做大量运算 | 按源 IP 限速；超限直接走借壳路径（不额外增加代价） |
| **front 站不可达** | 借壳路径失效，节点行为异常 | 启动时探测；运行期定期健康检查；不可达时**拒绝新连接**而非退化 |
| **front 选择本身成为特征** | 若全车队使用同一 front，仍是单一字符串 | 每节点独立配置 front；front 需满足：真实、可达、流量大、TLS 1.3 |
| **REALITY 类方案已被研究** | 本设计属于该家族，公开分析已存在 | 见 §9：重点不是"选一个永久安全的方案"，而是建立特征失效的可观测性 |

### 8.3 明确不在威胁模型内

- 节点私钥泄漏（此时一切失效，属运维范畴）
- 端点被控
- 审查者接受极高误报率的全面封禁（此时任何伪装都无意义）

## 12. 可行性验证

§4.4 的判别机制依赖两个 uTLS 能力，其中任一不成立都会使整份设计作废。两者已用可执行测试验证，代码在 [`spike/feasibility_test.go`](spike/feasibility_test.go)，`go test ./docs/tessera/spike/` 可复现。

验证对象：`github.com/metacubex/utls v1.8.4`（本仓库现有依赖，未新增）。

### 12.1 结论

| 待验证项 | 结果 |
|---|---|
| 能否改写 `legacy_session_id` | ✅ 可原地等长覆盖 |
| 能否取得线路上那个 X25519 key_share 的私钥 | ✅ `State13.KeyShareKeys.Ecdhe` 的公钥与线路上 `0x001d` 条目**逐字节相同** |
| 改写后 TLS 握手是否仍能完成 | ✅ 与真实 Go TLS 1.3 服务端握手成功，协商 `0x0304` |
| 改写是否引起指纹漂移 | ✅ 无漂移，仅 `[39:71]` 32 字节不同，1726 字节的 ChromePQ ClientHello 其余完全一致 |
| 判别是否真的能区分 | ✅ 未改写的原生浏览器 ClientHello 解封失败 |
| AAD 绑定是否有效 | ✅ 换一个 front 域名解封失败 |

第二项是存亡点：服务端从线路上读到的 key_share 派生共享密钥，客户端**必须**用那把私钥而非另生成一把，否则两侧密钥不同、每条连接都会静默落进借壳路径。四个指纹（Chrome_120_PQ / Chrome_Auto / Firefox_120 / Safari_16_0）全部通过。

### 12.2 实测中暴露的、凭推理会做错的三处

1. **`KeySharePrivateKeys.CurveID` 恒为 `0x0000`**（未填充）。按它判断 `Ecdhe` 对应哪条曲线会得到错误结论；只能按 group 从线路上取 `0x001d`。
2. **真实浏览器并列发送多个 key_share，且含 GREASE 条目。** Chrome PQ 是 `0x001d`(32B) + GREASE(1B) + `0x6399` X25519MLKEM768(1216B)。取"第一个 key_share"或"最长的 key_share"都会取错。GREASE 的 group 值逐指纹变化（实测见到 `0x3a3a` / `0x7a7a` / `0xeaea`），必须跳过而非枚举。
3. **AEAD 容量必须精确核对。** 16 字节明文 + 16 字节 tag = 32 字节，与 `session_id` 恰好吻合，一字节都不多。任何增加明文字段的改动都会溢出这个字段，届时只能牺牲字段或另找载体。

### 12.3 本次验证未覆盖的

- **服务端侧的完整实现**：`Raw` 解析器是为测试写的最小实现，真实服务端还需处理分片、超长 ClientHello、恶意构造的长度字段。
- **变体 B**（出示 front 真实证书链）——未验证服务端 TLS 栈能否绕过"证书与私钥必须匹配"的约束。
- ~~认证路径与借壳路径的时序差~~ —— **已测量，见 §13。**
- ~~**QUIC 路径**~~ —— **已验证，见 §6**（另有代码 [`spike/quic_test.go`](spike/quic_test.go)）。
- **front 清单的两项硬门槛**（审查网络内是否被 SNI 过滤、节点侧可达性）—— 见 §14.5，均需本机以外的观测点。

## 13. 时序旁路：测量与缓解

代码在 [`spike/timing_test.go`](spike/timing_test.go)，`go test ./docs/tessera/spike/` 可复现；真实站点测量需 `K2T_NET=1`。

### 13.1 攻击

借壳路径必须先拨到 front、再等它的 ServerHello；认证路径在本地立刻回。观察者**主动探测一次**即可拿到该节点的借壳时延基线，此后**被动观察**就能把每条流按"回得快 / 回得慢"打标——**回得快的就是认证用户**。

这条路径不需要攻破 §4.4 的任何密码学环节。**判别机制被绕过而非被破解。**

### 13.2 测量结果

可分性 = 最优单阈值分类器的准确率。**该指标在有限样本下有向上偏置**（它取多个候选阈值中的最大值），因此必须先测出同分布对照的地板，读数只有相对地板才有意义——与 50% 比较会得出错误结论。

模拟参数：node→front RTT 30ms ± 15ms，每组 120 样本。

| 场景 | 可分性 | 相对地板 | 判定 |
|---|---|---|---|
| **地板**（同分布对照，n=120） | 56.7% | — | 指标本身的噪声 |
| **无缓解** | **100.0%** | +43.3pt | 完全可分。auth p50=161µs vs relay p50=64ms |
| 固定延迟（补借壳均值） | 68.8% | **+12.1pt** | **不够**——中心对齐但方差不对齐 |
| **按分布采样延迟** | 58.3% | +1.6pt | 落在噪声内 |
| 采样延迟 + 预热连接池 | 57.9% | +1.2pt | 落在噪声内，且代价更低 |

**真实 front 站握手时延**（本机实测，`K2T_NET=1`）：

| 站点 | p50 | p95 | p5–p95 跨度 |
|---|---|---|---|
| www.microsoft.com | 63ms | 182ms | 128ms |
| www.apple.com | 63ms | 370ms | 314ms |
| www.amazon.com | 55ms | 182ms | 140ms |
| www.wikipedia.org | 98ms | 193ms | 100ms |

现实的天然抖动（100–314ms 跨度）远大于模拟的 ±15ms。这对防御**有利**——分布越宽越难分辨——但也意味着延迟代价按实测 p50 计在 55–98ms 量级。

### 13.3 v1 规范要求

1. **认证路径必须延迟首字节响应。不得使用固定延迟**——实测显示补均值只把可分性从 100% 降到 68.8%，仍显著高于 56.7% 的地板。中心对齐而方差不对齐，观察者依旧能分。

2. **延迟应取自现场测量，而非存档分布的采样。**
   节点在服务一条认证连接的同时，对 front 做一次真实的借壳时延测量（可复用连接池），用该测量值作为本次延迟。
   理由是 §13.4 的实测结论：存档分布是真实分布的**有限样本近似**，其抽样误差可被足够耐心的观察者检出，且所需 profile 规模随攻击者观测量增长；而现场测量在构造上**没有逼近误差**，等价于实测中始终落在零假设内的"完美知识"配置。
   若因成本必须退回存档采样，profile 规模须 **≥ 10 倍于预期攻击者观测量**（§13.4 实测），并持续滚动刷新。**注意这引入一个矛盾：规模够大就意味着积累周期长（10⁵ 样本按每分钟 2 次需约 35 天），而期间网络状况已漂移，"同分布"前提自我瓦解。** 这正是推荐现场测量的原因。

3. **应维护到 front 的预热连接池。** 它省掉借壳路径的一次 TCP RTT，实测把认证用户的伪装代价从 68ms 降到 38ms，同时收窄两条路径的方差。

4. **冷启动必须显式处理。** 节点刚启动、样本不足时不得以零延迟服务认证连接——那等于在启动窗口内把所有早期用户暴露。样本达到阈值前，认证路径应使用保守的固定上界，或直接不接受连接。

5. 延迟只加在**连接建立**阶段，不影响建立后的每次请求。对 VPN 场景，55–98ms 的一次性开销可接受。

### 13.4 大样本下的残余：已定论

§13.2 的 n=120 结论不能外推到攻击者聚合大量连接的情形。首次测量（socket 谐架、每配置单次）读数在 +6.8 与 −3.0 之间摇摆，噪声与效应量同量级，**不足以下任何结论**。此处补做了有功效的实验，代码见 [`spike/residual_test.go`](spike/residual_test.go)。

**方法**：丢弃 socket 与 sleep，直接对时延建模，换取每配置 30 次重复与 95% 置信区间。时延用**对数正态**（真实 front 是长尾的，见 §13.2 的 p95 与跨度，均匀抖动不能代表）。丢掉 OS 与网络噪声是**刻意的保守选择**——真实抖动同时落在两条路径上、只会压低可分性，因此无噪模型是攻击者能力的**上界**。

**方法学纠正（第一次分析是错的）**：最初以"各策略自身的同分布地板"为零假设。这是循环论证——profile 小会让填充延迟落在离散取值上，**从而抬高该策略自身的地板**，于是把漏洞本身写进了零假设。按此读数，`profile=200` 显示负残余、看起来最安全，**实际上它是最危险的一行**。正确的零假设是"完美知识"配置（填充直接取自真实分布，两侧同分布，测得值即纯粹的有限样本偏置）。下表已按修正后的零假设重算。

**结果**（攻击者聚合 n 条连接）：

| 填充策略 | n=2000（零假设 51.44%） | n=20000（零假设 50.45%） |
|---|---|---|
| 完美知识（即零假设，对照） | 51.52% (+0.08) 落在零假设内 | 50.44% (−0.01) 落在零假设内 |
| profile=200 | 52.95% (**+1.50**) ★ 可利用 | 53.06% (**+2.61**) ★ 可利用 |
| profile=2000 | 51.61% (+0.17) 落在零假设内 | 51.12% (**+0.67**) ★ 可利用 |
| profile=20000 | 51.30% (−0.15) 落在零假设内 | 50.54% (+0.08) 落在零假设内 |
| profile=200 + 核平滑 | 53.35% (**+1.91**) ★ 可利用 | 52.63% (**+2.18**) ★ 可利用 |
| profile=2000 + 核平滑 | 51.75% (**+0.31**) ★ 可利用 | 51.37% (**+0.91**) ★ 可利用 |

**结论一：核平滑无效，且会变差。** `profile=2000` 加平滑后超出量从 +0.67 升到 +0.91。我原本假设病因是取值离散，**该假设被证伪**。真实病因是经验分布的**抽样误差**（profile=200 的经验 CDF 与真实 CDF 相差 O(1/√200)≈7%），平滑不修这个，反而加宽分布、偏离更多。

**结论二：所需 profile 规模随攻击者观测量增长。**

| 攻击者 n | profile=1×n | profile=10×n | profile=100×n |
|---|---|---|---|
| 2 000 | +0.16 落在内 | +0.04 落在内 | −0.12 落在内 |
| 20 000 | +0.10 落在内 | −0.03 落在内 | −0.02 落在内 |
| 200 000 | +0.04 ★ 可利用 | −0.00 落在内 | +0.00 落在内 |

`profile ≥ 10×n` 在所有测试点都落在零假设内。`profile = 1×n` 在 n=200000 时统计显著，但超出量仅 **+0.04pt**（50.18% vs 50.14%）——**可检测，但操作上无价值**。

值得注意的是零假设自身随 n 收敛到 50%，绝对可利用信号同步缩小；所以"攻击者只要等得够久就赢"这个直觉**不成立**。真正的约束是：**对固定规模的 profile，足够耐心的攻击者终会捞到信号**（`profile=2000` 在 n=2000 安全、n=20000 就 +0.67pt）。

**结论三：因此推荐现场测量而非存档采样**（§13.3 第 2 条）。要靠增大 profile 顶住，需积累 10⁵ 量级样本；按每分钟 2 次约需 35 天，而这段时间内网络状况已漂移，"同分布"前提自我瓦解。现场测量没有逼近误差、没有积累期，等价于始终落在零假设内的"完美知识"配置。

**本节未覆盖**：真实（非对数正态）分布及其随时间漂移下的行为；现场测量会使每条认证连接额外产生一次到 front 的连接，**该行为本身是否构成新信号，未分析**。

### 13.5 其余未覆盖

- 仅覆盖 **ClientHello → 首字节响应**。握手完成后的时序特征（首个应用数据的时机、连接时长分布）属于流量形状，见 §8.2，仍是缺口。
- 模拟采用均匀抖动；真实分布是长尾的（见 13.2 的 p95 与跨度）。按分布采样在原理上适配长尾，但**未在真实长尾分布上验证**。
- 借壳路径的时延还取决于 front 站自身的负载波动，节点无法控制；该成分是否引入可利用的相关性，未分析。

## 14. 流量形状：一个测得到的轴，和一个我们取不到的零假设

代码在 [`spike/shape_test.go`](spike/shape_test.go)；真实站点测量需 `K2T_NET=1`。

### 14.1 它和本文其余各项的区别

前面每一处暴露都是**一次性构造问题**：ClientHello 造对、凭据放对字段、证书补到位——做对一次，此后不再泄漏。流量形状不是。它在连接活着的每一秒持续泄漏，且握手期的任何精细处理都碰不到它。

### 14.2 实测

两条**真实** TLS 会话，打向**同一个真实站点**，唯一差别是使用方式。测量在 TLS 之下的 TCP 层，因此记录尺寸就是观察者看到的密文尺寸。

| front | 用法 | 时长 | 上行 | 下行 | 记录数 | 最长静默 | 活跃占比 |
|---|---|---|---|---|---|---|---|
| www.apple.com | 浏览（取一次页面后闲置） | 20s | 1719 | 257 708 | 34 | 20s | 0.05 |
| www.apple.com | 隧道式（持续往返） | 19s | 2826 | 2 514 352 | 142 | 2s | 0.55 |
| www.microsoft.com | 浏览 | 20s | 1727 | 14 174 | 8 | 20.1s | 0.05 |
| www.microsoft.com | 隧道式 | 20s | 2870 | 56 879 | 31 | 2s | 0.55 |

### 14.3 这些数字证明了什么、没证明什么

**必须分清，否则会重犯 §13.4 的错误**（当时我拿被测策略自身的地板当零假设，把漏洞藏进了零假设里）。

- **「最长静默」「活跃占比」两列是构造出来的**，不是发现。间隔 2s、闲置 20s 是我选的参数。这两列描述的是我写的两个计划，不是世界。
- **下行体量与记录数不是构造的**——它们来自站点真实的页面尺寸（9.8× / 4.0×）。这两列是真数字。
- **隧道侧是下界，不是上界。** 20 秒 10 次请求，比起真实 VPN 会话（小时级、GB 级、持续双向）微不足道。

**而真正的零假设是「该 front 真实用户会话的分布」，我们取不到。** 没有观测点去采样别人站点的用户行为。一个在 apple.com 上点了二十分钟的真人，其会话同样是"持续往返"。因此本节**不能**给出可分性结论，只能给出轴的量级。

### 14.4 因此设计怎么走

零假设取不到，就不能走"证明我们落在分布内"这条路，只能走**按构造使分布重叠**。两条路径：

**路径 A：front 按流量类别选，而不是按知名度选。**

判据从"真实、可达、流量大、TLS 1.3"（§8.2）**修订为**：该站的**正常用户本来就持有长时、大流量、双向的连接**。

> 这直接推翻了一个隐含选择：**`www.apple.com` 与 `www.microsoft.com`——§13 用作时序基线的那两个站——不满足该判据。** 它们的正常连接就是"取一次页面然后闲置"，恰是表中被隧道侧甩开 4–10 倍的那一行。知名度高不等于适合借壳。

候选类别：流媒体 / 视频、云存储与同步、会议、WebSocket 长连接应用、大对象 CDN。代价是这些站点通常按域名分片、CDN 前置，L4 的「SNI 与 IP 不匹配」问题（§5）在它们身上是否更容易被容忍，**未评估**。

**路径 B：限制单条外层连接的时长与体量，超限即换新连接**，把一条长隧道拆成若干条 front 式的短会话。代价有两处：连接频次本身成为新特征；且每次换连接都要重做握手，包括 §13.3 的时序缓解开销。

v1 需在 A / B（或二者叠加）之间裁决。**本节不做这个裁决**——它取决于 front 清单（未决问题 4），两者应一并定案。

### 14.5 front 判据的一次普查

工具在 [`tools/front_survey.py`](tools/front_survey.py)。把 §14.4 的判据落成三条可测量的轴，跑了一遍候选池。

**发现：**

1. **`/24` 分散度比 IP 数有判别力得多。** `www.bing.com` 有 20 个 IP，却只落在 **2 个 /24** 里——审查者枚举两个网段就能建立"合法 IP 集合"。`s3.amazonaws.com` 的 32 个 IP 散在 **29 个 /24**，枚举成本完全不同。只看 IP 数会把 bing 排在前列，是错的。
2. **控制组符合 §14.4 的预测，且 `www.wikipedia.org` 在 L4 上最差**：单 IP、单网段、解析无分歧——"SNI 与 IP 不匹配"在它身上是零成本判据。
3. **两个 Microsoft 下载 CDN 的证书验证失败。** 我第一眼把这读成"出局"，**这个读法是错的**：借壳路径转发的是探测者自己的 ClientHello，它拿到的正是该主机名的真实响应——真实用户也会拿到同样的证书错误，P2 不受影响。它的真实含义是另一回事：**这个名字平时不承载浏览器式 TLS**，而我们的认证流量正好长得像浏览器式 TLS。是一条有具体理由的警示，不是否决。

**本次普查测不到、因而未决案的：**

- **该域名是否在审查网络内被 SNI 过滤**——这是**硬门槛**（front 的名字若本身被过滤，每条连接第一个包就死），需要审查网络内的观测点。
- **从节点可达**——本次在开发机上测，位置就是错的，必须在节点上复跑。
- **front 是否拒绝数据中心 IP**——节点是云 IP，本机不是，测不出来。
- **单点测量低估全球 IP 分散度**：geo-DNS 使这里的 IP 数是本地视角下的数字，真实分散度更高。需多地复测。

因此**未决问题 4 仍未定案**，但判据已可执行、候选池已缩小，且排除了"按知名度选"这个默认做法。

### 14.6 可能永久不可测

采样 front 真实用户分布需要一个我们没有、且大概率永远不会有的观测点。这不是"暂时未做"，而应作为**设计约束**接受：任何依赖"我们已证明落在正常分布内"的论证在本项上都不可用。§9 的可观测性流程在此处退化为**间接指标**——被封禁率、单节点存活时长——而非直接的分布比对。

## 附录 A：普查方法与可复现性

§1.2 的数据由 `dig -t TYPE65` 查询 DNS HTTPS 记录、解析 SvcParam key 5（`ech`）、再按 draft-ietf-tls-esni-18 解出 `config_id` 与 `public_name` 得到。

注意：macOS 自带 `dig` 9.10.6 不认识 `HTTPS` rrtype，直接使用 `dig HTTPS <domain>` 会静默退化为 A 记录查询并返回空结果——**这会造成"无 ECH 部署"的假阳性结论**。必须使用 `-t TYPE65` 并自行解析通用格式。

普查脚本应纳入 §9 的定期测量，与基线数据一同入库。
