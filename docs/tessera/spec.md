# Tessera 协议规范（`k2t`）

**版本**：Draft v0.1
**日期**：2026-07-27
**状态**：设计草案，未实现，未定案

---

## 1. 为什么需要它

### 1.1 k2v5 伪装层的结构性缺陷

k2v5 用**"ClientHello 里有没有 ECH 扩展"**来判断一条连接是不是自己人（`server/server.go` `handleRawTCP` 检查 `info.HasECH`）。

**这是一个明文的、任何人都能观察和伪造的标志位。** 由此产生两个可直接利用的后果：

**后果一：一次连接即可证伪节点身份。** 探测者发送一个带 ECH 扩展、但 `config_id` 为垃圾值的 ClientHello：

1. `PeekClientHello` 看到 `0xfe0d` 扩展 → `HasECH = true`
2. 进入 `handleK2V5` → `tls.Server(conn, s.TLSConfig).Handshake()`
3. Go 的 TLS 栈找不到匹配的 ECH 密钥 → ECH 被拒，但**握手继续**（client-facing server 行为，回送 `retry_configs`）
4. 服务端出示自签名证书 → **探测者拿到一张给 `cloudflare-ech.com` 签发、CA 验证不通过的证书**

证书补多长都无济于事——问题不在长度，在签发者。

**后果二：最常见的良性流量反而触发暴露路径。** Chrome 在没有真实 ECH 配置时会发送 **GREASE ECH 扩展**。因此任何一个 Chrome 用户偶然访问节点的 443 端口，都会被判定为"自己人"、进入 `handleK2V5`、拿到自签名证书——而不是被伪装反代导向一个正常网站。伪装在最高频的场景下失效。

### 1.2 ECH 的伪装前提已经过期

k2v5 协议规范 §3.1 的核心假设是：

> Cloudflare uses a single `public_name` for all ECH-enabled sites, so all legitimate Cloudflare ECH traffic shares the same outer SNI — **our traffic blends in naturally**.

**2026-07-27 实测普查（78 个域名 × 3 个独立 resolver：1.1.1.1 / 8.8.8.8 / 9.9.9.9）：**

| 结果 | 数量 |
|---|---|
| DNS HTTPS 记录中发布 `ech=` 的域名 | **2** |
| 其中不同的 `public_name` 数量 | **1**（`cloudflare-ech.com`） |
| 观察到的 `config_id` 取值 | **1**（`128`） |
| 有 HTTPS 记录但**不含** `ech=` | 24（含 `cloudflare.com` 自身、`discord.com`、`digitalocean.com`、`hubspot.com` 等全部受测 Cloudflare 托管站） |
| 无 HTTPS 记录 | 52 |

仅存的两个是 `cloudflare-ech.com` 与 `crypto.cloudflare.com`（Cloudflare 的演示端点）。**Cloudflare 已对客户域名关闭 ECH。**

结论：

- **可供混入的 ECH 流量池已不存在。** 那句假设在写下时（Cloudflare 2023 年曾大范围启用 ECH）可能成立，今天不成立。
- **真正的指纹是 ECH 扩展本身，而非其中写了什么名字。** 线路上出现 `encrypted_client_hello` 已属极稀有事件。在此前提下调整 `public_name` 属于在已暴露的维度上做微调。
- **附带发现的具体不一致**：现实世界唯一在用的 `config_id` 是 `128`；生产节点实测为 `150 / 245 / 247`（`GenerateECHKeyFromTemplate` 伪造为 `tmpl.ConfigID + 1`，且各节点抓取模板的时刻不同）。`config_id` 是**明文上线**的，因此即使外层 SNI 写着 `cloudflare-ech.com`，`config_id` 也与当前真实值对不上。

### 1.3 因此

Tessera 不是对 k2v5 伪装层的修补，而是替换它的判别机制与探测应答机制。隧道层（stream 复用、设备认证、拥塞控制）全部保留。

## 2. 威胁模型

假定审查者具备以下能力：

| 能力 | 说明 |
|---|---|
| **T1 被动指纹** | 记录并分类 ClientHello（JA3/JA4：扩展集合与顺序、GREASE、cipher 顺序、ALPN、supported_groups）、SNI、证书长度 |
| **T2 被动流量分析** | 包长分布、时序、方向性、连接时长、并发模式 |
| **T3 主动探测** | 对可疑 IP:port 主动发起连接，构造任意输入，观察响应 |
| **T4 DNS 关联** | 查询任意域名的 A/AAAA/HTTPS 记录，比对 SNI 与目的 IP 的一致性、比对域名是否真的部署某项特性 |
| **T5 统计分类** | 对流量特征做 ML 分类，容忍一定误报率 |
| **T6 长期观察** | 跨时间关联同一 IP、同一客户端的行为模式 |

假定审查者**不具备**：破解 X25519 / AEAD、在端点上执行代码、获取节点私钥。

**关键判据**：任何具备"零误报"性质的检测规则都是致命的——审查者可以无代价地封禁。设计的目标是让所有可用规则都带有不可接受的误报率。

## 3. 设计原则

按重要性排序。后面的每一条设计决策都可以回溯到这里。

**P1. 判别必须靠秘密，不能靠标志。**
区分"自己人"与"探测者"的依据，必须是只有持私钥者才能产生、观察者既无法复现也无法证伪的密码学证明。协议标志位、扩展存在性、端口、包长——任何可观察量都不合格。

**P2. 主动探测必须无法证实。**
不存在任何输入能让节点暴露自己。探测者得到的响应必须真实到可以通过 CA 验证。这要求未认证路径的响应**来自真实站点本身**，而非我们的模仿。

**P3. 各层必须自洽。**
TLS 指纹 / SNI / 证书 / IP / DNS / 流量形状——六层中任何一层与"我们声称的身份"对不上，都会把"常见"变成"唯一"。审查者的标准手法正是：用常见特征过滤出候选集，再用那一处不一致精确定位。

**P4. 不依赖人群存在。**
任何"混入某类流量"的设计都必须回答：那类流量今天还有多少？谁在维持它？它消失时我们怎么知道？ECH 是活教训——假设过期了两年而无人察觉。**特征时效性必须被持续测量，而非一次性论证。**

## 4. 协议规范

### 4.1 术语

| 术语 | 含义 |
|---|---|
| **front** | 被借壳的真实网站，例如 `www.example-major-site.com`。必须真实存在、从节点可达、部署 TLS 1.3 |
| **node** | 运行 Tessera 的服务端（k2s） |
| **short_id** | 8 字节客户端组标识，用于多租户区分与吊销 |
| **认证路径** | 判别成功，进入 k2 隧道 |
| **借壳路径** | 判别失败，整条连接被透明转发给 front |

### 4.2 密钥材料

节点持有一对长期 X25519 密钥 `(S_priv, S_pub)`，随节点置备生成并持久化。

`S_pub`（32 字节）通过连接 URL 分发给客户端，与 `front` 域名、`short_id` 一同下发。**`S_priv` 永不离开节点。**

### 4.3 连接 URL

```
k2t://<host>:<port>?pbk=<base64url(S_pub)>&front=<front域名>&sid=<hex(short_id)>&ip=<拨号IP>
```

- `host` — 内层标识，任意值（沿用 k2v5 语义：证书不按域名校验）
- `front` — 外层 SNI 与借壳目标
- `ip` — 实际拨号地址；`host` 不做 DNS 解析（沿用 k2v5 的 `wire.Config.Host` 语义）

### 4.4 客户端：ClientHello 构造

客户端使用 uTLS 以**真实浏览器 ClientHelloSpec**（当前基线：Chrome）构造 ClientHello，SNI 设为 `front`，随后在序列化前改写两个字段：

**第一步 — key_share。**
生成临时 X25519 密钥对 `(C_priv, C_pub)`，将 `C_pub` 作为 TLS `key_share` 中 x25519 组的公钥。这是浏览器本来就会发送的字段，形态无异常。

**第二步 — 派生认证密钥。**

```
shared  = X25519(C_priv, S_pub)
authKey = HKDF-Expand(HKDF-Extract(SHA-256, salt = C_pub, IKM = shared),
                      info = "k2t/v1 auth", L = 44)
          → key   = authKey[0:32]     (ChaCha20-Poly1305 密钥)
          → nonce = authKey[32:44]    (12 字节)
```

`shared` 因 `C_priv` 为每连接临时生成而唯一，故 `key` 亦唯一；**因此确定性 nonce 是安全的**（不存在同密钥重用 nonce 的情形）。

**第三步 — 构造 session_id。**

明文（16 字节）：

| 字段 | 长度 | 说明 |
|---|---|---|
| `version` | 1 | 协议版本，v1 = `0x01` |
| `flags` | 1 | 保留，v1 置 0 |
| `timestamp` | 4 | Unix 时间，分钟精度（大端） |
| `short_id` | 8 | 客户端组标识 |
| `reserved` | 2 | 置 0 |

```
session_id = ChaCha20Poly1305_Seal(key, nonce, plaintext = 上表16字节, aad = front域名的UTF-8字节)
           → 16 字节密文 + 16 字节 tag = 32 字节
```

TLS 1.3 的 `legacy_session_id` 恰为 32 字节且浏览器填随机值，**容量精确吻合，无需额外携带任何字节**。

`aad` 绑定 `front`，使得截获的 `session_id` 无法搬到伪装成其他站点的节点上重放。

### 4.5 服务端：判别

节点在 443 端口接受 TCP，`Peek` 出完整 ClientHello（复用现有 `wire.PeekClientHello` 基础设施），然后：

1. 提取 `legacy_session_id`。长度 ≠ 32 → **借壳路径**。
2. 提取 `key_share` 中的 x25519 公钥 `C_pub`。不存在 → **借壳路径**。
3. `shared = X25519(S_priv, C_pub)`，按 §4.4 同法派生 `key` / `nonce`。
4. `AEAD_Open(key, nonce, session_id, aad = 本节点的 front 域名)`。失败 → **借壳路径**。
5. 校验 `version` 已知；`timestamp` 在 ±`REPLAY_WINDOW`（默认 ±10 分钟）内；`short_id` 在本节点有效集合内。任一不满足 → **借壳路径**。
6. 校验 `session_id` 未在重放缓存中出现（LRU，容量与 `REPLAY_WINDOW` 匹配）。命中 → **借壳路径**。
7. 全部通过 → **认证路径**。

**判别结果对观察者不可见**：两条路径在 ClientHello 层面输入完全相同，差异仅存在于服务端的私钥运算结果。

### 4.6 借壳路径

节点与 `front:443` 建立 TCP 连接，将**原始 ClientHello 字节原封不动**转发过去，随后双向管道直至任一端关闭。

关键性质：

- 探测者收到的是 **front 的真实证书链**，CA 验证通过
- 探测者进行的任何后续交互（HTTP 请求、TLS 特性协商）得到的都是 front 的真实响应
- 节点不产生任何自己的 TLS 材料，**不存在可供比对的伪造痕迹**

要求：

- `front` 必须从节点网络可达；启动时探测一次，不可达则拒绝启动（**失败必须显式，不可静默退化**）
- 借壳连接受并发信号量限制（复用现有 `proxySem`），过载时直接关闭连接——与"服务器繁忙"无异
- 借壳连接的读写超时应与真实浏览过程相称（非 k2 隧道的长连接参数）

### 4.7 认证路径

节点自行完成 TLS 握手。客户端已通过 §4.4 完成认证，**不做 CA 校验**（不做域名匹配，不做签名链验证）。

证书的处理有两个变体：

**变体 A（v1 采用，实现简单）**
节点出示自签名证书，长度经 `tlspad` 补齐至 `front` 证书链的实测长度（复用现有 `ProbeTarget` + `GeneratePaddedCert`）。

TLS 1.3 中证书是加密传输的，观察者只能测量加密握手记录的**大小**。补长使该大小与 front 相称。

> **注意**：这意味着**证书补长机制在 Tessera 下仍然承重**，不应退役。它从"给伪造证书打补丁"变成"让认证路径的握手尺寸与借壳路径一致"。

**变体 B（目标形态）**
节点获取并缓存 front 的**真实证书链字节**，在认证路径中原样出示，用自己的密钥签署 `CertificateVerify`。客户端不验签。观察者看到的握手在字节层面与真实访问 front 无异。

变体 B 需要在客户端与服务端两侧修改 TLS 栈（服务端需绕过"证书与私钥必须匹配"的约束）。**列为目标形态而非 v1 范围。**

### 4.8 隧道层

认证路径的 TLS 建立后，其上承载的内容**完全复用 k2v5 现有实现**：

- WebSocket 升级至 `/k2v5/tunnel` 或直接 smux（沿用现状）
- stream 类型、metadata 设备认证（`0x10`）、准入门（`admissionPolicy`）
- k2cc 拥塞控制

**Tessera 只替换"如何建立一条不被识别的加密通道"，不触碰通道内的任何东西。**

## 5. 六层一致性清单

P3 要求逐层自洽。当前设计在各层的状态：

| 层 | 处理 | 状态 |
|---|---|---|
| **L1 TLS 指纹** | uTLS + 真实浏览器 spec，两条传输统一 | ⚠️ 需补齐：QUIC 路径当前无 uTLS（见 §6） |
| **L2 外层 SNI** | front 的真实域名 | ✅ 自洽 |
| **L3 证书** | 变体 A 补长 / 变体 B 真证书 | ✅ 借壳路径完全真实；认证路径见 §4.7 |
| **L4 IP** | SNI 与目的 IP 不匹配 | ❌ **无解**（除非自建 CDN 或公开节点 IP，后者等于把节点列表交给审查者）。靠 P2「探测无法证实」兜底 |
| **L5 DNS** | 不需要我们发布任何记录 | ✅ front 自身的记录天然存在且真实 |
| **L6 流量形状** | 未处理 | ❌ **v1 已知缺口**（见 §8） |

**L4 是本设计承认的残余风险。** 它无法在不暴露节点 IP 列表的前提下消除。设计的赌注是：审查者若仅凭"SNI 与 IP 不匹配"就封禁，会误伤大量 CDN、企业前置代理、灰度环境等合法场景。这个赌注需要持续验证（见 §9）。

## 6. QUIC：未解问题

Tessera v1 **仅定义 TCP 路径**。QUIC 无法直接套用同一设计：

- QUIC Initial 包用**可从 Destination Connection ID 推导的密钥**加密，审查者能解出其中的 ClientHello。§4.4 的 `session_id` 机制本身仍然工作（判别不可见性成立），但——
- **借壳转发在 QUIC 上做不到 TCP 那样干净**：QUIC 的连接 ID 与包保护绑定在端点上，无法把一条 QUIC 连接原样转交给 front。
- 若对未认证的 QUIC Initial **静默丢弃**，会产生新的可检测模式：审查者观察到该 IP 有 QUIC 流量、但主动探测无响应 → "存在仅响应授权客户端的服务" → 恰是规避工具的典型特征。

候选方向（均未验证）：

1. **QUIC 不在伪装端口提供**：客户端先经 TCP 路径认证，再由服务端下发 QUIC 的端口/令牌。代价是首次连接延迟。
2. **QUIC 端点自行扮演合法 h3 服务**：对未认证 Initial 返回真实 h3 服务器面对未知请求时的响应。需要节点实际托管一个站点。
3. **接受 QUIC 为较弱路径**：TCP 路径按本规范做满，QUIC 维持现状，按网络环境择优。

> **这是本设计最大的缺口。** QUIC 是当前主传输，意味着 Tessera 的收益初期只覆盖一部分流量。不应在此问题解决前宣称"伪装已修复"。

## 7. 与 k2v5 的关系与迁移

**Tessera 是新增传输类型，不替换、不修改 k2v5。**

| 阶段 | 内容 |
|---|---|
| 1 | 节点同时监听 k2v5（现状）与 Tessera。互不干扰 |
| 2 | Center 按客户端版本决定下发 `k2v5://` 或 `k2t://` tunnel URL |
| 3 | 新客户端优先 Tessera，失败回落 k2v5 |
| 4 | 新版本铺开至足够比例后，逐节点关闭 k2v5 传输 |

存量客户端**零感知、零改动**——它们从未收到 `k2t://` URL，行为与今日完全一致。向后兼容性由"新增而非修改"这一结构保证，不依赖迁移期的小心操作。

## 8. 安全分析

### 8.1 本设计消除的攻击

| 攻击 | 消除方式 |
|---|---|
| 主动探测证伪身份 | 任何未通过 §4.5 的输入都得到 front 的真实响应；不存在能让节点暴露自己的输入 |
| Chrome GREASE ECH 误判 | 判别不再依赖任何扩展的存在性 |
| ECH 扩展本身作为稀有信号 | 不发送 ECH |
| `config_id` 与真实世界不一致 | 无 ECH 配置，无 `config_id` |
| 自签名证书泄漏 | 借壳路径不产生我们的证书；认证路径的证书对观察者仅体现为长度 |
| 跨节点重放 `session_id` | AEAD 的 `aad` 绑定 front；`short_id` 绑定节点有效集合 |
| 同节点重放 | timestamp 窗口 + LRU 重放缓存 |

### 8.2 残余风险与已知攻击面

| 风险 | 说明 | 缓解 |
|---|---|---|
| **L4 SNI/IP 不匹配** | §5 已述，无解 | 靠 P2 兜底；持续测量误报率假设是否成立 |
| **L6 流量形状** | 认证路径承载的是 VPN 流量，其包长/时序分布与浏览 front 显著不同。**长期观察（T6）可据此分类** | v1 不处理。这是继 QUIC 之后的第二大缺口 |
| **两条路径的时序差** | 认证路径本地完成握手；借壳路径需额外一次到 front 的 RTT。**该差异可测量** | 认证路径可注入等量延迟；需实测标定。**v1 必须处理，否则 P1 被时序旁路架空** |
| **X25519 计算 DoS** | 每条入站连接触发一次 X25519（约 50µs 量级）。攻击者可低成本迫使节点做大量运算 | 按源 IP 限速；超限直接走借壳路径（不额外增加代价） |
| **front 站不可达** | 借壳路径失效，节点行为异常 | 启动时探测；运行期定期健康检查；不可达时**拒绝新连接**而非退化 |
| **front 选择本身成为特征** | 若全车队使用同一 front，仍是单一字符串 | 每节点独立配置 front；front 需满足：真实、可达、流量大、TLS 1.3 |
| **REALITY 类方案已被研究** | 本设计属于该家族，公开分析已存在 | 见 §9：重点不是"选一个永久安全的方案"，而是建立特征失效的可观测性 |

### 8.3 明确不在威胁模型内

- 节点私钥泄漏（此时一切失效，属运维范畴）
- 端点被控
- 审查者接受极高误报率的全面封禁（此时任何伪装都无意义）

## 9. 可观测性：特征时效性

**这是 P4 的落地要求，也是本次设计中最重要的流程改变。**

ECH 的教训是：一个核心设计假设过期了约两年而无人察觉，直到一次偶然的实测普查。这不能靠运气。

要求建立**定期自动化测量**，至少覆盖：

| 测量项 | 用途 | 频率 |
|---|---|---|
| 现实世界 ECH 部署面普查（DNS HTTPS 记录中的 `public_name` / `config_id` 分布） | 验证任何"混入某类流量"假设是否仍成立 | 每周 |
| 各 front 站的可达性、证书链长度、ALPN、TLS 版本 | 借壳路径有效性；变体 A 的补长目标是否漂移 | 每日 |
| 主流浏览器 ClientHello 指纹基线 | uTLS 预设是否落后于真实浏览器版本 | 每月 |
| 认证路径与借壳路径的时序分布 | §8.2 时序旁路是否被拉开 | 持续 |

任何一项偏离基线，应产生告警而非静默。**测量脚本与基线数据须与代码同仓、同评审。**

## 10. 未决问题

需在进入实现前定案：

1. **QUIC 路径怎么办**（§6）——三个候选方向均未验证。这是最大缺口。
2. **变体 A 还是变体 B**（§4.7）——v1 建议 A，但需确认 A 的握手尺寸吻合度是否足够。
3. **时序对齐的具体做法**（§8.2）——认证路径注入多少延迟、如何标定、是否随 front 变化。
4. **front 清单从哪来、由谁分配**——每节点独立配置已定，但选取标准与分配机制未定。
5. **uTLS 是否支持改写 `session_id` 与指定 key_share 私钥**——REALITY 在 uTLS 上实现了同类机制，故推断可行，**但本项目尚未验证**。这是实现可行性的前置条件。
6. **`short_id` 的分配、下发与吊销**——与 Center 的设备体系如何衔接。
7. **流量形状**（§8.2）——是否纳入 v1，还是明确留给后续。

## 11. 与既有决策的冲突

本设计与 2026-07-27 讨论中确立的若干方向存在冲突，需明确裁决：

| 既有决策 | 本设计的处理 | 说明 |
|---|---|---|
| 删除 uTLS | **反转** | uTLS 从"可有可无"变为承重结构——整套方案的前提是我们的 ClientHello 与真实浏览器不可区分。且需补齐 QUIC 侧 |
| 保留证书补长 | **保留，且更重要** | 在变体 A 下，补长承担"让认证路径与借壳路径的握手尺寸一致"的职责（§4.7） |
| 外层 SNI 管过墙、内层管真实内容 | **保持** | Tessera 中外层 SNI = front（过墙伪装），内层标识任意（k2v5 语义不变） |
| 不影响旧客户端 | **保持，且由结构保证** | 新增传输而非修改，存量客户端从未收到 `k2t://` URL（§7） |
| public_name 白名单 + 每节点随机 | **作废** | 实测证明现实世界只有一个 `public_name`，白名单无素材（§1.2）。该需求由"每节点独立 front"承接 |

## 附录 A：普查方法与可复现性

§1.2 的数据由 `dig -t TYPE65` 查询 DNS HTTPS 记录、解析 SvcParam key 5（`ech`）、再按 draft-ietf-tls-esni-18 解出 `config_id` 与 `public_name` 得到。

注意：macOS 自带 `dig` 9.10.6 不认识 `HTTPS` rrtype，直接使用 `dig HTTPS <domain>` 会静默退化为 A 记录查询并返回空结果——**这会造成"无 ECH 部署"的假阳性结论**。必须使用 `-t TYPE65` 并自行解析通用格式。

普查脚本应纳入 §9 的定期测量，与基线数据一同入库。
