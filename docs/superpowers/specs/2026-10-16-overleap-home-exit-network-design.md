# Overleap 家庭出口网络：技术方案与工作量评估

- 日期：2026-10-16
- 状态：**设计稿，未批准实现**。实现和上线都要 David 本人确认。
- 提出方：growth（产品目标见 growth 仓库 `todos/overleap.md`，经济账见 `strategy/overleap-paid-tor-economics-2026-10-16.md`）
- 范围：只讨论 Overleap。开途不接入、不感知这套网络。

## 0. 结论先行

1. **现有代码不能直接做两跳。** k2 现在的「中继」只转发 App 访问 Center 的请求，而且中继节点自己解开会话、看得到明文；k2v5 链接没有「经过 A 再到 B」的写法；k2s 不能躲在家庭 NAT 后面接客。三块都要新做。
2. **推荐的做法叫「反向挂接」**：
   - 主机的出口程序主动连到我们的入口（TCP 443，跟普通 HTTPS 一样），不开任何端口，所以 CGNAT 后面也能用。
   - 会员照常连入口。连上后，在入口隧道里再开一条**直通出口、端到端加密的内层隧道**。
   - 入口只负责把这条内层隧道拼到主机挂上来的连接上，看到的是密文，**不知道去哪**。
   - 出口只看到流量来自我们的入口，**不知道是谁**。出口不需要、也拿不到会员的账号凭据。
3. **试点最小范围约 40–55 人日**，单人全职约 9–11 周。最大的两块是 k2 协议层（入口挂接、出口运行时、客户端两跳）和 Center（出口注册、分配、计量）。OpenWrt 安装包不在试点范围里。
4. **上线前必须先修两件跟这个项目无关、但已经存在的问题**（第 9 节）：
   - k2s 默认在 INFO 级别记录每个连接的目的地址和 DNS 域名，跟 Overleap 隐私政策第 3.5 条「不记录访问的网站」冲突；
   - 节点注册接口是首次使用即信任，任意 IP 都能注册进共享节点池。
5. **隐私承诺要说准**：两跳分离能防住主机知道「谁」，也能防住入口（和它的日志）知道「去哪」。但入口和分配表都是我们自己运营的，**对我们自己来说只是制度保证，不是密码学保证**（我们理论上能按时间关联）。所以对外不能说成「跟 Tor 一样」。

## 2. 总体架构

```
会员设备 ──外层 k2v5（ECH，抗封锁，用会员凭据认证）──▶ 入口（我们的机房 k2s）
   │                                                │
   └── 内层隧道（TLS 1.3，固定出口证书指纹） ──────────┼──▶ 主机挂上来的那条连接
                                                    │        （主机主动外连，TCP 443）
                                                    ▼
                                          家庭出口（主机电脑/Docker）
                                                    │
                                                    ▼
                                                 目标网站
```

**谁知道什么**

| 角色 | 知道 | 不知道 |
|---|---|---|
| 入口 | 会员是谁（账号、设备）、连的是哪个出口、字节数 | 目的地（内层是密文） |
| 出口主机 | 目的地址、域名（SNI）、入口的 IP | 会员是谁、会员的 IP。出口拿不到会员凭据，所有流量都经入口进来 |
| Center | 分配表（出口 ↔ 候选会员）、每个出口每天的总量 | 目的地；也不存「谁哪天用了哪个出口」 |
| 网站 | 家庭 IP | 会员是谁（会员自己登录了网站账号的情况除外） |

**为什么不让出口认证会员**：出口根本不开放端口，唯一的入站路径是它自己挂到入口的那条连接。入口已经认证过会员、核过分配关系，出口只要相信「从我挂的那条连接进来的都是入口放进来的」就够了。这样出口进程里就不会出现会员凭据，主机即使改程序也偷不到。

## 3. 设计要点（逐条回应 growth 的 8 个问题）

### 3.1 两跳链路

**协议**

- **主机挂接**：出口程序用一个「主机凭据」（绑定主机自己的 Overleap 账号，见 3.2）以新模式 `mode=exit-attach` 连入口。走现有的 TCP+TLS+WebSocket+smux 通道（`k2/wire/tcpws.go`），因为 TCP 443 外连在任何家庭网络都通。入口登记「出口 ID → 这条会话」。
- **会员开内层**：会员在外层隧道里打开一条流，目标是一个保留的虚拟地址，比如 `x-<出口ID>.exit.invalid:443`。入口在 k2s 的 TCP 处理里识别这个保留后缀，先查分配表，确认这名会员被分配了这个出口，再把这条流拼到出口挂接会话里新开的一条流上，不去公网拨号。
- **内层协议**：在这条拼好的流上跑 TLS 1.3，证书指纹固定为出口在挂接时登记的公钥（Center 随订阅下发）。TLS 里面直接复用 k2 现有的流协议，包括按连接带目标地址、以及经流转发 UDP。出口一侧用 `server.New` 的处理器，只是监听器换成「从挂接会话里收到的流」。
- **需要新写的适配器**：
  - 客户端：把「外层隧道的 Dialer」包装成内层 wire 客户端要的 `DirectDialer`（`k2/wire/wire.go:28-31`）；
  - 出口：把挂接会话包装成 `net.Listener`。

**入口看到的**只有「会员 A 连了出口 X 的保留地址」加上密文。所以入口的这条日志也必须去掉（见第 9 节），否则「会员 ↔ 出口 ↔ 时间」就落盘了。

**性能**

- **多出来的延迟**：入口到家庭出口的往返（同国约 20–60ms），加上家庭上行的排队。入口和出口要放在同一个国家：美国出口配美国入口。
- **吞吐**：瓶颈是主机的上行带宽。美国有线宽带上行通常 10–35 Mbps，光纤常见 300 Mbps 以上，被分配到这台出口的会员共享它。每个出口 20 名会员是「分配上限」，不是同时在线数；同时在线一般 2–5 人。
- **外层是 QUIC 时**，内层是 TCP 流套在 QUIC 流里，没有「TCP 套 TCP」的拥塞叠加。**外层是 TCP 时**会有队头阻塞，丢包网络下更慢。
- **UDP**（比如 HTTP/3、游戏）在内层走「经流转发」，比外层直接用 QUIC 数据报慢。试点接受这一点；网站一般会自动退回 TCP。
- **加密做两遍**：手机耗电和 CPU 都会增加，试点期间要实测。

**考虑过、没选的方案：k2p + TURN**

- 做法：用现有 k2p，限定只走我们自己的 TURN 中继，家庭端用 WebSocket 外连信令。复用更多现成代码。
- 没选的原因：
  1. 依赖 STUN、TURN、ICE 三套东西，而且 k2p 的鉴权和证书都还没加固；
  2. QUIC 再套在外层隧道的 UDP 里，有 MTU 和拥塞控制叠加的问题；
  3. TURN 协议特征明显，封闭网络里的会员如果直连 TURN 会被封，而套进外层隧道又回到了第 2 条的问题；
  4. ICE 一旦没限定好，就会尝试直连，把会员 IP 暴露给主机。

  反向挂接只用到已经在线上跑着的 k2s 和 wire，需要动的东西更少。

### 3.2 主机端软件

**一份 Go 程序，三种外壳。** 出口运行时放在 k2 里（新包，比如 `k2/exit`），由它负责：挂接、内层 TLS、出站拨号、限速、流量上限、暂停，以及屏蔽规则（3.5）。

| 外壳 | 试点 | 说明 |
|---|---|---|
| Docker 镜像 | ✅ | 只需外连；不映射端口、不加特权、不挂 docker.sock；只读根文件系统。镜像名、路径、日志名都用 Overleap 命名（见 3.8） |
| 桌面 App「共享」开关（macOS / Windows） | ✅ | 出口运行时放进现有的 k2 守护进程，作为与客户端并行的第二个组件。设置页加一个「共享我的网络」：开关、带宽上限、每月流量上限、暂停到某时、本月转发量和服务人数。第一次打开时必须先看完主机告知书（growth 起草），点同意才能开 |
| OpenWrt 安装包 | ❌ 第二期 | k2r 现在只是客户端网关，要加出口模式并在各种架构上打包，3–5 人日，另外还要上真机 |

**NAT、CGNAT、IPv6**

- **NAT 和 CGNAT**：只要能出站 TCP 443 就能挂接，跟主机网络在哪一层 NAT 后面无关。
- **出口 IP 由出口自己上报**：出口定期查询自己的出站 IP，并通过挂接会话上报。CGNAT 下这个 IP 是运营商的共享公网 IP（跟邻居共用），这对「像真人」反而有利。会员连接走的是入口，不需要知道出口 IP，所以**家庭 IP 变了，会员无感**。
- **IPv6**：试点只做 IPv4 出站（k2 本来就过滤 AAAA 记录）。挂接本身可以走 IPv6。

**限速、限额、暂停**

- 限速：出口用令牌桶限制总带宽，按主机设定的上行上限来。
- 限额：达到每月流量上限后自动断开挂接，下月 1 日恢复。
- 暂停：立刻断开挂接，Center 同时把这个出口标成离线。会员那边的现有连接会断开，客户端按 3.3 自动换出口。
- 主机自己正在用网时不想被抢带宽：试点先不做自动让路，只靠带宽上限。

**电脑睡眠或关机**：等同于出口下线，会员自动换走。所以桌面主机的可用率会比 Docker 主机低，分配时要考虑进去（3.3）。

### 3.3 分配

**新表**

| 表 | 字段 | 说明 |
|---|---|---|
| `home_exits` | `id`、`host_user_id`、`region`、`status`（online/offline/paused/flagged/retired）、`pubkey_pin`、`egress_ip`（当前）、`asn`、带宽和流量上限、`last_attach_at` | 出口不进 `slave_nodes`，因为那张表按 IPv4 识别，而家庭 IP 会变。出口 ID 跟着主机凭据走，不受 IP 变化影响 |
| `home_exit_assignments` | `exit_id`、`user_id` | 只存这两个字段，**不带时间**，满足「只保留节点 ↔ 候选会员」 |

**算法**（试点规模很小，用贪心加定期重平衡就够）

1. 会员第一次需要家庭出口时（付费会员开通，或在 App 里选「家庭出口」），按地区偏好，从 online 且已分配人数少于 20 的出口里挑 k 个。k 默认 3，可配置为 2。
2. 打分时优先选：已分配人数少的；跟会员现有出口不同的主机、不同 ASN、不同 /24 网段的（避免「同一家运营商一起被标记」）；以及历史在线率高的（桌面主机权重低一点）。
3. 凑不够 k 个时，能分几个就分几个，其余由机房出口兜底。这就是「尽量分配，不硬锁定」。
4. 出口变成 `flagged` 或 `retired` 时，把它从所有分配里移除，并为受影响的会员补分配。`offline` 只是临时状态，不移除分配，但下发订阅时不再列出它。
5. 每天重平衡一次：已分配人数超过 20 的（比如上限被调低了）挪走一部分；一直分不满的会员补上。

**下发**：沿用 `/api/subs` 和隧道列表接口。对 Overleap 会员，在原有的机房隧道之外，再加上他名下的家庭出口：

```json
{ "url": "k2v5://…入口…?exit=<出口ID>&exitpin=<指纹>", "ipType": "residential", "kind": "home_exit", "label": "Home exit · US East" }
```

- 会员**只拿得到出口 ID 和证书指纹，拿不到主机 IP**。这比「出口名单不公开」更进一步：连被分配到的会员也不知道主机是谁、在哪里。会员访问一个查 IP 的网站当然能看到出口 IP，这一点避免不了，也无所谓。
- 这里的 `?exit=` 是新参数。旧客户端不认识它，会把这条当成普通入口直连，也就是从机房出去。体验退化但不会坏，所以兼容。不过为了避免会员误以为自己走的是家庭出口，Center 只给声明支持两跳的客户端版本下发这一类条目（按客户端上报的版本判断，用哪个字段待实现时定）。

**自动切换**

- **出口掉线**：内层连不上，会走现有 `NextURL` 的排除逻辑（`k2/subscription/manager.go`），先换到会员的下一个家庭出口，都不行再换机房出口。这里要改的是 Pick：同一会员的条目里，家庭出口排在机房出口前面（现在 Pick 根本不看 ipType）。
- **IP 被情报库标记**：监控（3.6）把出口标成 `flagged` 后，Center 移除分配。客户端每 30 分钟刷新一次订阅（`refresh=1800`），刷新后就换掉了。要更快可以让 Center 通过入口直接断开该出口的挂接，客户端立刻失败转移。
- **会员手动「换一个出口」**：App 隧道列表加一个按钮，强制排除当前出口、重新挑选。这就是 growth 估过的「被拦时一键换出口」，在这个方案里顺带做掉。

### 3.4 计量与分成

- **以入口的统计为准，不信出口自报**。主机能改自己的程序，自报的数字可以造假；入口在拼接时能数清每个出口转发了多少字节。
- **新表 `home_exit_daily`**：`exit_id`、`date`、`bytes_up`、`bytes_down`、`distinct_members`（当天经这个出口的不同会员**数**，只存数，不存名单）、`online_seconds`。
- **入口在内存里按天去重会员**（集合只在内存里，当天上报完就丢），只把计数报给 Center。
- **会员自己的用量仍走现有的按设备计量**。它记录「设备 × 节点 × 天」，这里的「节点」是入口，不是出口，所以不会形成「会员 × 出口 × 时间」。**这一点要写成测试守住**：设备计量里不能出现出口 ID。
- **结算**：按 `home_exit_daily` 汇总每个主机每月的转发量和服务人数，套 growth 定的分成规则。现金分成还是会员互助，算法一样，只是输出不同：会员互助就给主机账户加时长，用现有的 `applyGiftCredit`。试点期间只做报表和后台人工发放，不做自动打款。

### 3.5 屏蔽高风险用途

在出口运行时的出站拨号处统一检查。入口不检查，因为入口看不到目的地。

| 规则 | 试点 | 说明 |
|---|---|---|
| 内网、回环、链路本地、CGNAT、组播 | ✅ 已有 | 复用 `checkAddr`。还要加上**主机自己的公网 IP 和网关**（防止通过回环访问主机的路由器管理页） |
| TCP 25 | ✅ | 发垃圾邮件最直接的途径。587 和 465 需要账号认证，保留 |
| BitTorrent | ✅ | 拦三样：协议握手（`\x13BitTorrent protocol`）、DHT 和 uTP 的特征（UDP 包体以 bencode `d1:a`/`d1:r`/`d1:q` 开头）、常见 tracker 的 announce 路径。识别规则参考客户端现有的 `SniffBT`。拦不干净，目标是挡住默认配置的下载工具，降低主机收到版权投诉的概率 |
| 每个会员的速率上限 | ✅ | 防止一个人占满主机带宽，按内层会话计算 |
| SMB、RDP 这类扫描常用端口 | 第二期 | 看试点期间的投诉情况再定 |

DNS 由出口用内置的 DoH 解析（固定几家公共解析服务），不用主机网络里的解析器，避免被主机或运营商的 DNS 篡改。

### 3.6 监控

新增一个 Center 定时任务 `worker_home_exit_reputation.go`，每天对每个出口跑一轮。

**情报库**（对出口当前上报的出站 IP）

| 来源 | 判定 | 备注 |
|---|---|---|
| ip-api | `hosting` / `proxy` | **免费版只允许非商业用途**，商用要买 Pro（约 $15/月）或换别家 |
| proxycheck | `proxy`、`type` | 免费每天 1000 次，试点够用 |
| IPQS / Spur / ipinfo privacy | `vpn`、`proxy`、风险分 | growth 的成功标准里点名了这几家，都是付费的，试点挑一家买最低档 |

**真实站点探针**：经过这个出口发请求（Center 用一个内部监控账号，走正常的两跳路径），复用 10-15 实测的判别规则，查 YouTube 机器人验证页和 Reddit 403；再加一两个美国站点，比如 Bank of America 登录页、Amazon。每个出口每天约几十 KB，对主机流量的影响可以忽略。

**判定**

- 任一付费情报库把它标成 VPN/代理，或者 YouTube/Reddit 连续两天被拦，就标 `flagged`。随后自动移除分配并通知主机，因为 IP 被标记了，主机也可能想换 IP，比如重启光猫。
- 每周输出「被标记出口数 / 总出口数」，对应 growth 成功标准里「家庭 IP 被情报库标记的天数」这一项。7 天内普遍被标记就停止试点，这个判断由人来做。

**节点健康**：挂接在线时长、最近一次挂接、上行吞吐（入口测得）、内层握手失败率，都在管理端的出口列表里显示。

### 3.7 和现有住宅 IP 标、`/api/subs` 的关系

- **`ip_type=residential` 是现有节点（机房/VPS）的属性**，由运营方在 `.env` 里声明，比如将来买的 SolaDrive。家庭出口是另一类东西，不进 `slave_nodes`，但下发给客户端时也带 `ipType: residential`，这样 App 现有的「Residential IP」徽标直接复用。
- **App 侧要做的**：
  - 把家庭出口单独分一组（「你的家庭出口」），因为它们是分配给你的，而不是公共的；
  - 加「换一个出口」按钮；
  - 守护进程的 Pick 认识 `kind`（3.3）。
- **SolaDrive 这类住宅 IP VPS 在这套设计里的位置**：它是普通的 k2s 节点，用 `ip_type=residential` 标记，会员直连，不需要两跳。可以当作家庭出口不够时的「第二档兜底」，排在家庭出口之后、普通机房出口之前。
- **开途**：`/api/subs` 在 kaitu 品牌下完全不返回家庭出口；`home_exits` 只允许 Overleap 账号当主机。入口挂接只在声明了 overleap 的入口上开启。

### 3.8 复用开途和 k2 底层，以及品牌隔离

**能复用的**：k2 协议栈（wire、server、engine 都是共享协议层，不属于任何品牌）、Center 的鉴权和计量框架、桌面守护进程、隧道列表 UI。

**主机端是新的暴露面。** 主机能看到镜像名、文件路径、进程名、日志和服务名，而现在这些地方到处都是 `kaitu`：

| 位置 | 现在 | 主机端必须 |
|---|---|---|
| Docker 镜像 | `public.ecr.aws/…/k2-sidecar` 等 | 新开 Overleap 命名空间的镜像，不复用节点用的 sidecar 和 compose |
| 路径和日志 | `/etc/kaitu`、`/var/log/kaitu` | `/etc/overleap-exit` 之类 |
| 默认 Center 地址 | `k2.52j.me` | 用 Overleap 的域名（入口挂接地址也是） |
| 桌面服务名 | 两个品牌都叫 `kaitu`（`desktop/CLAUDE.md:35-37`） | 共享开关会让主机去看服务列表，这个遗留问题会更显眼；至少界面和日志里不能出现。要不要借这次把服务改名，单独评估 |

**守卫**：现有的 `check-desktop-brand-purity.sh` 只拦 `kaitu.io` 和 CDN 路径，允许裸 `kaitu` 字样。出口镜像要加一个更严的检查（镜像里 `strings` 扫出 `kaitu`/`开途` 就失败），并接入构建流程。

## 4. 主机侧的安全边界

- **主机能看到什么**：目的 IP 和端口、TLS 的 SNI、明文 HTTP 的全部内容、流量大小和时间。**看不到**会员是谁、会员 IP、HTTPS 内容。主机告知书和会员说明都要如实写。
- **恶意主机**能做的：记录或篡改明文 HTTP；屏蔽某些网站；把「某出口的 20 名候选会员的访问记录」卖给第三方（但没有身份）。缓解办法：
  1. 推荐制加主机门槛：账号年龄、付费记录；
  2. 监控探针顺便检查「通过出口拿到的内容是否被改」，用固定的金丝雀页面比对哈希；
  3. 提醒会员敏感操作只用 HTTPS（现在绝大多数网站本来就是）。
- **伪装成主机的监视者**，比如某个国家机构批量注册主机来观察流量：推荐制能挡住大部分。设计上让每个会员的出口分散在不同主机、不同 ASN 上，单个主机只能看到一部分流量。
- **会员滥用，后果落到主机头上**：滥用流量从主机的 IP 出去，投诉也会到主机。设计上我们**无法**从出口反查到具体会员，只能把范围缩小到「该出口的候选会员」。这正是我们承诺的隐私属性，代价是滥用者难以追查。处理办法：
  - 主机可以随时下线；
  - 出口被投诉后标 `retired` 并重新分配；
  - 如果多个出口的投诉集中在同一批候选会员上，按交集排查。这是有意保留的最低限度追查能力，要不要在隐私政策里说明，由 David 和法务决定。
- **主机的 LAN 安全**：出口进程不能访问主机的内网（3.5 的第一条规则）。Docker 版本身就隔离在容器网络里；桌面版运行在 root 守护进程里，规则必须在拨号前检查，测试要覆盖「目标是主机网关」「目标是主机自己的公网 IP」这两种情况。
- **运营商条款**：美国大多数家庭宽带（Comcast、Charter/Spectrum 等）的使用条款禁止在家里运营服务器或转售带宽。主机被运营商限速或销户，是影响主机留存的主要风险（growth 经济账第 1 个敏感变量）。这属于法律和条款层面的风险，按 growth 的口径由主机自己评估，但技术方案无法规避它。

- **入口放在哪**：复用现有 Overleap 的 AWS 美国节点，还是单开一台专门做入口。专门一台的好处是挂接和普通流量互不影响，日志策略也单独管。

## 9. 前置修复（不论做不做这个项目都该修）

### 9.1 k2s 记录目的地

`k2/server/handler.go:420-425`（`HandleTCP` 在 INFO 级别记录 `remote` 和 `addr`）、`:482-489`（UDP 同样）、`:810` 和 `:820`（DNS 查询的域名）。日志默认级别是 info（`k2/config/config.go:391`），车队用的 `docker/docker-compose.yml` 也是 `K2_LOG_LEVEL=${K2V5_LOG_LEVEL:-info}`。日志写到 `/var/log/kaitu`（lumberjack 保留 7 天）和 journald。

Overleap 隐私政策第 3.5 条写的是「We do not record your network activity content, including websites visited」。**同时服务两个品牌的节点上，Overleap 用户的访问目的地现在会在节点上保留几天**，跟这一条冲突。

修法：把这几条日志里的目的地字段去掉，或者降到 debug（生产不开 debug）。只调日志级别不够，因为别的 INFO 诊断也需要。改动在 k2 子模块，要按车队流程滚动升级。是否需要对已有日志做清理，由 David 决定。

### 9.2 节点注册是首次使用即信任

`api/route.go:593`：`PUT /slave/nodes/:ipv4` 不经过 `SlaveAuthRequired`。对一个从没见过的 IPv4，请求里带什么 `secretToken`，就把它当成这个节点的密钥（`api/slave_api_node.go:276-357`），节点由此加入共享池。节点自己声明 `brands`，而运营方的 `visible_*` 开关默认是开的。

如果有人用一台自己的服务器注册进来，并且通过了后续上报，真实用户就有可能被分配到这台机器。这台机器能看到用户的 `udid:token`（`k2/wire/stream.go:243-249`）和全部目的地。

我还没有验证从「注册」到「被用户选中」中间有没有其他门槛，比如诊断任务、离线判定、证书和 ECH 配置的校验，**所以这条只是「需要核实」，不是「已确认可以利用」**。家庭出口不走这条注册路径（3.3）。共享池本身是否要改成准入制（比如注册前由运营方预先登记 IP 和密钥），作为独立事项处理。
