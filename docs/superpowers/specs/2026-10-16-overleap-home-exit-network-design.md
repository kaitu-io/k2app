# Overleap 家庭网络互换：技术方案与工作量评估（修订版）

- 日期：2026-10-16（v2，同日修订）
- 状态：**设计稿，未批准实现**。实现和上线都要 David 本人确认。
- 需求来源：growth（`todos/overleap.md`）。v2 按 David 10-16 定的「对等互换」模型改写。v1 的「主机给会员当出口」模型被取代，但它的反向挂接、分配表、入口计量、屏蔽、监控、品牌守卫都保留，见第 3 节。
- 范围：只做 Overleap。开途以后可以作为内部客户接入，这次不做。

## 0. 结论先行

1. **模型**：每个会员在自家宽带上接一台设备，自己的网络给别人当出口，同时用别人的家庭网络出去。分两档：
   - **隐私档**（默认）：经过我们的入口中继，主机不知道是谁。
   - **直连档**：先打洞直连，失败再走中继，双方能看到彼此的 IP。
2. **试点工作量约 69–98 人日**。比 v1（40–57）多出来的是：直连档（k2p 加固和打洞）、所在地与方向限额、积分账本、面向大陆的抗封锁入口和挂接、设备镜像。单人约 14–20 周，两人约 8–10 周。直连档放第二期可降到约 60–86 人日；桌面共享开关也放第二期，约 56–80 人日（第 8 节）。
3. **打洞成功率**：只做 UDP 加 IPv6，不做 TCP 打洞。按公开研究和行业经验估，海外家宽之间直连能成功的大约 **60–85%**；一端在对称 NAT 或运营商 CGNAT 后面会明显更低；**两端都是对称 NAT 基本失败**。这只是估计，试点要实测（第 4.1 节）。
4. **大陆**：
   - 所在地在大陆的会员，**直连档一律关闭**，强制经抗封锁入口中继。
   - 大陆家庭设备给境外会员当出口时，它的挂接也必须走抗封锁通道。
   - 理由：境外家庭 IP 封起来成本低，直连流量特征又明显，被识别后封的是主机的家庭 IP，主机受损。大陆家宽普遍在 CGNAT 后面，直连成功率本来也低。
5. **中继成本**：入口在两头都要收发，流量按用户流量的约 2 倍计。每名会员每月 40GB 时，普通线路约 $0.15–0.6/月，适合大陆的优质线路约 $0.6–1.2/月（第 4.2 节）。
6. **设备**：第一期推荐**「Docker 镜像 + 一份 arm64 系统镜像（树莓派或 N100 小主机直接刷）」**。预装盒子也用这份镜像，只是多了物流。OpenWrt 安装包的工程量是它的 3 倍左右，放第二期（第 3.9 节）。
7. **两个前置修复**（v1 第 9 节）仍然有效，不论做不做这个项目都该修：k2s 记录目的地；节点注册首次使用即信任。
8. **对外表述**：隐私档能做到「主机不知道是谁，入口不知道去哪」；但入口和分配表都是我们自己运营的，对我们自己只是制度保证。直连档要明确告诉双方「彼此看得到 IP」。

## 1. 现状：能复用什么、缺什么

（与 v1 相同，摘要）

- k2 的中继只转发控制面请求，并且会解开明文（`k2/server/control_plane.go`）。
- k2v5 链接没有链式写法（`k2/wire/wire.go:209-231`）。
- k2s 不能躲在 NAT 后面接客。
- k2p（pion/ice 的 P2P）：客户端已接通；家庭端没有生产入口程序；信令服务没挂到任何服务里；鉴权放开（`k2/wire/metadata_auth.go:68-71` 的 validator=nil）。
- k2s 已有屏蔽内网的检查（`k2/server/handler.go:69-102`）；没有端口和 BT 屏蔽。
- 按设备计量已有（`k2/server/device_traffic_reporter.go`）。
- 客户端已有跨节点失败转移（`k2/subscription/manager.go:53-91`）。Pick 不看 ipType。
- 住宅 IP 徽标链路已通。没有「一个节点对多个会员、最多 20 人」的可见性。
- 节点按公网 IPv4 识别，重启时整行删掉再重建。
- 没有 IP 信誉监控。
- 桌面服务名两个品牌都叫 `kaitu`。

## 2. 总体架构

```
             ┌──────────── Overleap 入口（我们的机房 k2s，抗封锁：ECH / 跳端口） ────────────┐
             │   · 会员外层隧道（会员凭据）      · 设备挂接（设备凭据，TCP 443 外连）            │
             │   · 隐私档：把会员的内层流拼到出口设备的挂接上（只见密文）                         │
             │   · 直连档：经挂接会话交换打洞候选地址（信令）；打洞失败时退回上一行的中继          │
             └──────────────────────────────────────────────────────────────────────────┘
   会员 A 的手机/电脑 ──────────────▶ 入口 ──────────────▶ 会员 B 家里的设备 ──▶ 网站
   （所在地 X，目标地 Y）                                   （所在地 Y，给 A 当出口）
          ╰──── 直连档：A ⇄ B 的设备 UDP 打洞成功后，QUIC 直连，不经过入口 ────╯
```

每个会员同时是两种角色：

- **用户**：手机或电脑上的 Overleap App，选好目标地，用别人的出口。
- **主机**：家里的设备（盒子、Docker 或桌面共享开关）挂到入口，给别人当出口。

### 谁知道什么

| 角色 | 隐私档 | 直连档 |
|---|---|---|
| 入口 | 谁、连了哪个出口、字节数；不知道目的地 | 谁、和哪台出口交换了信令；打洞成功后连字节数也不知道 |
| 出口设备的主机 | 目的地、SNI；不知道是谁，不知道对方 IP | 目的地、SNI、**对方的 IP**；仍然不知道账号 |
| 会员 | 只拿到出口 ID 和证书指纹，拿不到主机 IP | **能看到主机的家庭 IP** |
| Center | 分配表（出口 ↔ 候选会员，不带时间）、按天汇总的计量、积分账本 | 同左 |

## 3. 沿用 v1 的部分

### 3.1 反向挂接与内层（隐私档）

- **设备挂接**：家里的设备以 `mode=exit-attach` 主动连入口，走 TCP+TLS+WS+smux（`k2/wire/tcpws.go`）。
- **会员开内层**：会员在外层隧道里打开到保留地址 `x-<出口ID>.exit.invalid:443` 的流。入口先核对分配关系，再把这条流拼到出口的挂接会话上。
- **内层协议**：TLS 1.3，固定出口证书指纹（由 Center 下发），里面跑 k2 现有的流协议。出口一侧复用 `server.New` 的处理器。
- **为什么出口拿不到会员凭据**：出口不开放端口，唯一的入站路径就是自己挂到入口的那条连接，所以出口进程里不会出现会员凭据。
- **需要新写的适配器**：客户端把外层 Dialer 包装成 `DirectDialer`；出口把挂接会话包装成 `net.Listener`。

### 3.2 出口运行时

一份 Go 程序，放在 k2 里新建的包，比如 `k2/exit`。它负责：挂接加重连、内层 TLS、出站拨号、限速、每月流量上限、暂停、内置 DoH、屏蔽规则（第 3.5 节）、上报出站 IP、日志里不记录目的地。

### 3.3 分配表（不带时间）

| 表 | 字段 |
|---|---|
| `home_exits` | `id`、`host_user_id`、`country`、`status`（online/offline/paused/flagged/retired）、`pubkey_pin`、`egress_ip`、`asn`、`nat_type`（v2 新增，见第 4.1 节）、限速、流量上限、`last_attach_at` |
| `home_exit_assignments` | `exit_id`、`user_id`，只存这两个字段 |

### 3.4 计量

以入口的统计为准，不信出口自报。新表 `home_exit_daily`：`exit_id`、`date`、`origin_country`（v2 新增，按会员所在地汇总，用于第 5.2 节的互换优先）、`bytes_up`、`bytes_down`、`distinct_members`（只存数）、`online_seconds`。

**直连档的流量入口看不到**，只能由两端自报。这部分处理见第 5.3 节。

### 3.5 屏蔽

在出口的出站拨号处检查：
- 内网、回环、链路本地、CGNAT 和组播地址，加上主机自己的公网 IP 和网关；
- TCP 25；
- BitTorrent（握手、DHT 和 uTP 的特征、tracker announce）；
- 按会员限速。

### 3.6 监控

每天：情报库检查（ip-api 免费版禁止商用，要买 Pro 或换别家；proxycheck；IPQS、Spur 二选一买最低档），再经出口跑 YouTube、Reddit 和美国站点探针。被标记就移除分配，并通知主机。

### 3.7 和住宅 IP 标、`/api/subs` 的关系

家庭出口不进 `slave_nodes`，下发给客户端时带 `ipType: residential` 和 `kind: home_exit`，App 现有的徽标直接复用。兜底顺序：家庭出口 → 住宅 IP VPS（`slave_nodes.ip_type=residential`，比如 SolaDrive）→ 机房。这要求 Pick 改成识别 `kind` 和 `ipType`。

### 3.8 品牌守卫

主机端的镜像、路径、日志、服务名、默认 Center 地址全部用 Overleap 命名。出口镜像构建时加一道更严的检查：`strings` 扫出 `kaitu` 或 `开途` 就失败。

### 3.9 主机端形态（v2 修订：「买设备」怎么交付）

| 方案 | 工程量 | 运营成本 | 结论 |
|---|---|---|---|
| **Docker 镜像** | 1–2 人日 | 无 | ✅ 试点 |
| **桌面共享开关**（macOS/Windows） | 4–6 人日 | 无 | ✅ 试点。缺点：电脑睡眠就下线，适合当补充，不适合当「设备」 |
| **arm64 系统镜像**（树莓派 4/5、N100 一类小主机，刷好就能用，只接网线） | 2–3 人日（基于 Docker 镜像做一个最小系统，开机自动挂接，首次用网页或扫码绑定账号） | 用户自己买硬件；我们也可以代购预装 | ✅ **推荐作为第一期的「设备」** |
| 预装盒子（我们寄） | 工程量同上一行 | 硬件加运费约 $85/台（growth 经济账）、各国海关、售后 | 用上一行的镜像，运营决定要不要寄。**只用有线网口、不带 Wi-Fi 的盒子**，可以避开各国的无线电认证 |
| OpenWrt 安装包（装在会员自己的路由器上） | 6–10 人日：要支持多种 CPU 架构；闪存和内存小；MIPS 路由器性能差；开途 k2r 在真路由器上已经踩过一串坑，见运维记录 | 无 | ❌ 第二期。路由器同时转发 20 人的加密流量，低端机型 CPU 吃不消 |

结论：**arm64 镜像加 Docker 最省事**。两者是同一个运行时，只多一层系统封装；不用适配 MIPS，不涉及无线电认证。

## 4. 新增评估

### 4.1 打洞成功率

**做法**：用 k2p 现有的 pion/ice，候选地址通过设备的挂接会话交换（不需要再单独部署信令服务）。只做 UDP 打洞，外加 IPv6 直连；**不做 TCP 打洞**。TCP 同时打开在家用路由器上成功率很低，pion 也不支持，投入产出不划算。

**成功率估计**（文献和行业经验值，**还没在我们的用户上实测**）：

- Ford、Srisuresh、Kegel，*Peer-to-Peer Communication Across Network Address Translators*，USENIX ATC 2005：样本里约 **82%** 的 NAT 支持 UDP 打洞，TCP 约 64%。
- 按 NAT 类型组合：
  - 两端都是「锥形 NAT」（同一内网端口去任何目的地都映射到同一个外网端口，大多数家用路由器默认如此）：基本都能成功。
  - 一端是「对称 NAT」（每个目的地映射一个新的外网端口；很多移动网络和部分运营商 CGNAT 是这样），另一端是端口受限的锥形 NAT：大多失败。不做端口预测时基本失败；pion 不做端口预测。
  - 两端都是对称 NAT：失败，只能走中继。
- **CGNAT**：RFC 6888 要求运营商级 NAT 采用「与目的地无关的映射」，按这个规范实现的 CGNAT 能打洞；但实际有不少运营商、尤其是移动网络是对称映射。经过家里路由器加运营商 CGNAT 两层 NAT 后，成功率还会再降。
- **IPv6**：两端都有 IPv6 时没有 NAT，只有路由器上的防火墙，同时向对方发包通常就能打通。美国、印度、德国、法国的家宽 IPv6 普及率较高。**这是提高直连率最便宜的办法**。但 k2 现在会过滤 AAAA 记录，要注意这只是指「对目标网站」，打洞本身可以用 IPv6。

**估计**：海外家宽之间（设备一般接在家用路由器后面，用户端可能是手机网络）直连成功约 **60–85%**。用户端在手机网络上时取下限。

**试点怎么测**：
- 设备挂接时做一次 NAT 类型探测：用两个不同的 STUN 服务器比较映射到的外网端口，写入 `home_exits.nat_type`。
- 客户端每次打洞，上报结果（成功或失败、双方的 NAT 类型、用了 v4 还是 v6），**不带 IP**。
- 分配时，直连档会员优先分到锥形 NAT 的出口。

**直连档上线前必须补的安全项**（k2p 现在的 validator=nil）：
- 会员打洞前，先从 Center 拿一张**分配票据**：Ed25519 签名，内容是出口 ID、有效期 10 分钟和一个随机数，**不带用户 ID**。出口用 Center 的公钥验签，同时检查随机数没被用过。
- 出口证书指纹由 Center 随订阅下发，替换掉现在的自签证书加放开校验。
- 直连那一段仍然是 QUIC + TLS 1.3。主机和会员都看不到对方的明文以外的东西：主机本来就能看到目的地，会员看不到主机网络里的任何东西。

### 4.2 大陆：直连被阻断的可能，以及中继成本

**所在地在大陆的会员用境外家庭出口**：

- **直连档关闭**。
  1. 大陆到境外的长时间大流量 UDP，在晚高峰常被运营商限速或丢包，QUIC 尤其明显。开途的线上经验就是：UDP 质量差时要切到 TCP。
  2. 封锁方看到一个大陆家宽 IP 和一个境外家宽 IP 之间长时间加密直连，一旦识别，代价最低的做法就是直接封境外那个家庭 IP，主机受损，而且这个出口对所有大陆会员都废了。
  3. 大陆家宽普遍在 CGNAT 后面，部分是对称映射，打洞成功率本来就低。IPv6 在大陆普及率高，但入站常被运营商或光猫的防火墙挡住。
- 所以大陆会员**只走隐私档**，入口必须用开途那套抗封锁做法：ECH、跳端口、伪装 SNI、多入口失败转移。这部分代码在 k2 里，两个品牌共用，**但入口要用 Overleap 自己的域名和节点**：
  - 现在节点上那些伪装成 people.cn 的 SNI 是开途专用的，不能拿来给 Overleap 声明；
  - 共用 IP 的话，一个被封，两个品牌一起倒。

**所在地在大陆的会员当出口（给境外会员用大陆 IP）**：

- 设备从大陆往外挂接入口，走的也是抗封锁通道（TCP 443 外连，跟大陆客户端连开途节点是同一个方向、同一种流量）。
- 境外会员的流量要穿过封锁线进出大陆，**速度和稳定性会明显不如其他方向**。这个方向在限额里应单独设一个小的上限。
- 法律风险：大陆主机替境外用户转发流量，个人承担的风险跟其他国家的主机不在一个量级。growth 已经把这一点转达给 David，David 已经决定按规则开放；告知书里要单独写一段，并且由法务过目。

**中继成本**（入口两头都在收发）：

- 入口的出站流量约等于用户流量（下载发给会员，上传发给出口），入站也约等于用户流量。
- 只计出站的厂商：Vultr 约 $2.93/TB，超量 $0.01/GB；Linode 约 $5/TB。按每名会员每月 40GB，约 **$0.12–0.2/月**。
- 进出都计的厂商（Lightsail）：送达口径约 $7/TB，中继要再翻倍，约 **$0.56/月**。
- 大陆会员需要对大陆线路友好的入口：香港、日本，或者 CN2 GIA 这类优质线路。按两到四倍的单价算，约 **$0.6–1.2/月**。大陆可达性要用 cn-gw 实测。
- growth 经济账里「入口 $0.40/用户/月」对海外会员偏保守，**对大陆会员偏乐观**。直连档打洞成功的那部分会员，中继成本为零。

### 4.3 所在地、目标地与方向限额

**所在地**（每个会员只有一个）：

- 按访问 IP 判断。来源有两个：**会员家里那台设备的出站 IP**（稳定，代表他能贡献哪里的网络），以及 App 的访问 IP。
- **建议以设备的出站 IP 为准**。有设备的会员，所在地等于设备所在国家；还没接设备的，用 App 的访问 IP。否则会员出差时，手机 IP 一变，所在地也跟着变，会触发不必要的重新分配。这一点需要 David 确认，设计上做成可配置。
- 所在地变了（设备的出站 IP 换了国家），会员的方向全部改为新的所在地，原来的分配全部释放，重新排队。

**目标地**：会员自选，可以选多个。「目标地能不能等于所在地」做成配置项 `allow_same_country`，默认关。

**容量要把 k 算进去**：growth 给的公式是「容量 = 目标地可用家庭出口数 × 20」，算的是名额数。每个会员要占 k 个名额，所以**能服务的会员数 = 出口数 × 20 ÷ k**。比如美国有 30 台出口、k=3，最多 200 名会员能用美国出口。另外，这些名额是**所有来源地共享的**，所以每个方向的上限是在分同一块蛋糕。

**数据结构（最小实现）**：

```
member_location   (user_id PK, country, source: device|app, updated_at)
member_targets    (user_id, target_country, status: active|waitlisted, queued_at)   PK(user_id, target_country)
direction_caps    (origin_country, target_country, member_cap, enabled)             PK(origin, target)；空 = 不单独限，只受目标地总量约束
home_exits.country                                                                  出口所在国家（取自设备的出站 IP）
```

- `member_targets.queued_at` 只在候补时有意义；转为 active 时清空，所以分配表本身仍然不带时间。

**分配流程**（每次有会员新增目标地、出口上线或下线、所在地变化，以及每天定时重算）：

1. 对每个目标地 Y：可用名额 = online 出口数 × 20 − 已分配名额数。
2. 候补队列按优先级排序：**互换分**（第 5.2 节）从高到低，同分时按 `queued_at` 先后。
3. 依次给候补会员分配 k 个出口（分配规则同 v1：分散主机、ASN、/24，优先在线率高的，直连档优先锥形 NAT）。每成功一个，检查该方向是否已到 `direction_caps.member_cap`，到了就跳过这个方向的其他候补者。
4. 凑不够 k 个时：先用已有的家庭出口，不够的用住宅 IP VPS，再不够用机房，并且**保持候补身份**，有空位时补上。这就是「尽量分配，不硬锁定」。

### 4.4 积分账本

**原则**：只记字节数和金额，不记目的地，不记出口 ID 和会员的对应关系。

**数据结构（最小实现）**：

```
credit_accounts (user_id PK, balance BIGINT, updated_at)
credit_entries  (id, user_id, kind: earn|spend|purchase|grant|adjust, amount BIGINT,
                 period CHAR(7)  -- 'YYYY-MM'，只到月份
                 , weight_snapshot JSON  -- 记账时用的稀缺权重
                 , ref VARCHAR  -- 比如 stripe invoice id
                 , created_at)
direction_weights (target_country PK, weight DECIMAL, computed_at)   -- 每周重算
usage_monthly   (user_id, target_country, period, bytes)   -- 记账完成后删除
```

- **挣积分**：每月由 `home_exit_daily` 汇总，主机的每台出口转发的字节数 × 该出口所在国家的权重。
- **花积分**：入口按「会员 × 目标国家」在内存里累计字节数，每天写入 `usage_monthly`，月底记一笔 spend 后**删除这些行**。账本里只剩「某会员某月花了多少积分」。
  - 这比按天保留更保护隐私，但要接受入口重启时丢掉当天未写入部分的风险（每小时刷一次就够）。
- **稀缺权重**：`weight(Y) = clamp(需求(Y) / 供给(Y), 0.5, 3)`。需求取过去 30 天 Y 方向的流量，供给取 Y 的出口在线容量。每周重算一次，记账时把当时的权重写进 `weight_snapshot`，方便对账。
- **积分不够**：余额低于 0 时，先允许透支到一个下限（比如 −20GB 等值），超过下限就**降到机房出口**，直到补足。
  - 「付费补」第一期用后台人工补（kind=purchase），第二期接 Stripe 一次性付款：Overleap 已有 Stripe，加一个 Price 和一个 webhook 分支，约 3 人日。
- **会员费和积分的关系**由 growth 定。比如年费每月附赠一定额度的积分，就是每月一笔 grant。账本本身不需要改。

### 4.5 两档对数据的不同影响

- **隐私档**：所有字节数由入口测得，记账可靠。
- **直连档**：流量不经过入口，只能由两端自报。出口报「我转发了多少」，客户端报「我用了多少」。
  - 两边对不上（差异超过 20%）时，按较小值记账，并标记异常。
  - 长期偏差大的主机降低权重，或者取消直连资格。
  - 防刷：自报只能在有效分配票据的范围内计；同一张票据重复上报不计。

## 5. 互换优先与公平

### 5.1 互换的含义

如果会员 A 的设备服务了「X → Y」方向的会员（A 在 Y，用户在 X），那么 A 要走「Y → X」时优先分配。

### 5.2 互换分

`reciprocity(A, target X) = 过去 30 天 A 的出口服务「所在地 = X」的会员的字节数`

- 数据来自 `home_exit_daily.origin_country`（第 3.4 节新增的字段），不涉及具体是哪个会员。
- 候补排序：先看互换分，再看积分余额，最后看排队先后。
- 互换分只决定**排队顺序**，不保留名额。否则冷门方向的主机会长期占着名额。

## 6. 风险（v2 新增；v1 的风险表仍然有效）

| 风险 | 影响 | 应对 |
|---|---|---|
| 打洞成功率不如预期 | 直连档大多数时候退回中继，中继成本上升 | 第 4.1 节实测；中继本来就是兜底 |
| 直连档泄露双方 IP | 会员知道主机的家庭住址范围（IP 能定位到城市）；主机知道会员 IP | 默认用隐私档；开启直连档时双方都要确认；主机可以设置「不接受直连」 |
| 供需失衡（大家都想去美国） | 美国方向候补排很长，热门方向没有空位 | 方向限额加积分权重；增长侧重点招热门地区的主机 |
| 所在地伪造（用 VPN 把设备伪装成别的国家） | 设备的出站 IP 就是它实际给别人用的 IP，伪造了也只是给别人提供了那个国家的出口 | 以设备的出站 IP 为准，本身就防伪造；App IP 只在没有设备时用 |
| 大陆入口被封 | 大陆会员全部掉线 | 开途那套抗封锁做法，加上多入口失败转移；**Overleap 入口和开途入口不共用 IP** |
| 大陆主机的法律风险 | 主机个人受损 | 告知书单独写，法务过目；David 已知悉 |
| 积分刷量（自己的两台设备互相刷） | 积分凭空产生 | 隐私档由入口计量；分配时不把会员分到自己的出口（同账号、同 /24 都排除） |
