# 召回优惠扁平化 + 召回效果统计 — 设计

日期：2026-11-03 · 决策人：David · 覆盖 `2026-11-03-ios-trial-recall-design.md` §5.5（活动码）

## 为什么

2026-04 至 11-03，召回邮件发出后 14 天内付款（按人去重）：

| 邮件 | 收件人 | 14 天内付款 | 用了码 |
|---|---|---|---|
| 未付款 1h（无折扣） | 148 | 36 | 0 |
| 未付款 1d（无折扣） | 122 | 12 | 0 |
| 未付款 3d（95 折 READY4U） | 108 | 5 | 0 |
| 未付款 7d（9 折 STAYFREE） | 104 | 5 | 0 |
| 未付款 14d（9 折 SMOOTHDAY） | 98 | 1 | 0 |
| 未付款 30d（85 折 KEEPGOING，「最后机会 / 最大优惠」） | 96 | 2 | 1 |
| 过期 7d（9 折 BACK90） / 30d（85 折 BACK85） | 59 / 61 | 2 / 0 | 0 |

- 付款几乎都发生在不带折扣的前两封提醒之后；越往后折扣越深，带来的付款越少，码基本没人用。
- 逐步加深的折扣会教用户「再等等更便宜」；95 折（约 $2.5）低于用户能感知的差额。
- 「7 天内有效」「本周内有效」是码本身并不执行的假期限（码都到 2036 / 2026-12-31）。会开通试用即关续订的人本来就多疑，假期限被识破的信任损失比折扣更贵。
- 「立减 $9.8 起，最高立减 $39.8」：最高那档是 5 年套餐，召回对象不会买；读者一算只能省 $9.8，反而失望。
- 没有对照组：上表连「1h 那 36 人里多少是被邮件打动的」都答不出来。

试用召回的人群（82% 开通即关续订，中位 1.8 分钟）卡在「怕被自动扣费」而不是价格——加深折扣只是补贴本来就会买的人，还会让第二年按原价续费看起来像涨价。

## 改了什么

**一类人一个优惠，所有阶段同一个，不加深**（`api/logic_recall_offer.go`）

| 人群 | 码 | 类型 | matcher | 用在 |
|---|---|---|---|---|
| 新客（从没付过费） | `NEW10` | coupon $10 | `first_order` | 试用召回 S1/S2、未付款 3d/7d |
| 老客（付过费、已过期） | `BACK10` | coupon $10 | `vip` | 过期 7d/30d |

- 年付 $49 → **$39**：整数价、首位 4→3；固定金额对长套餐占比小，不会再出现「最高立减」。新客老客力度相同，老客没有理由为了折扣故意断档。
- 邮件写具体价格：`OfferText` =「1 年 $39（平时 $49），折合每月约 $3.3」。锚点用用户真正见过的售价，不用划线价。
- 期限 = 活动码自己的截止日（`ValidDays` =「12 月 31 日前有效」），不写码不执行的期限。
- 标价与下单同一算法 `campaignPrice`（从 `applyCampaign` 抽出的纯函数）；**不能调 `applyCampaign`**，它会累加活动使用次数。
- 优惠阶段的码或年付套餐不可用 → 这些人本次不发 + Slack 告警（不发一封没有码的「优惠」邮件）。
- 链接统一 `PurchaseURL`：预填活动码与年付套餐、带 utm，邮箱在 fragment。

**阶段**

- 未付款：1h、1d 只提醒（不带折扣）→ 3d 第一次给 `NEW10` → 7d 再提一次同一个码。**14d / 30d 停发**。
- 过期：1d 只提醒 → 7d、30d 同一个 `BACK10`。
- 试用：S1 / S2 都是 `NEW10`。

**App 内（试用用户，Apple 订阅，不能提价格 / 官网）**：首页试用卡片、购买页试用结束标题下、续订关闭提示，统一加一句「扣费后也可随时在 App Store 关闭自动续订，已付期间照常使用」（新键 `purchase.iap.cancelAnytime`），S2 推送改为「订阅即恢复，之后可随时关闭续订」。这句是事实（Apple 订阅取消后用到期末），直接回应「怕被扣费」。

## 统计（`recall_stats`）

- 三条召回链路共用 `inRecallHoldout`（10%，盐沿用 `trial-recall-v1`，试用召回的分组不被打乱）。对照组不收信，落一行 `email_send_logs`：`status=skipped`、`error_msg=holdout`。未付款 / 过期召回自本次部署起有对照组。
- `GET /app/recall-stats?days=14&since=YYYY-MM-DD`（RoleMarketing）/ MCP `recall_stats`：按链路、按阶段给召回组与对照组的人数、窗口内付款人数、转化率、收入、用码人数、让利金额，及 `liftPoints`（召回组 − 对照组，百分点）。
- 付款 = 任意渠道未退款已付订单，落在 [首次记录, +days]；窗口没走完的人算 `pending`，不进分母。只算有邮箱的人（对照组是「本来会收到邮件」的人）。
- 判读：每组少于约 100 人时差值主要是噪声。**先跑满约 4 周再决定**：某阶段 lift ≈ 0 → 停掉它；带码阶段 lift 不高于前面的提醒 → 去掉折扣只提醒。

3. 改模板（kaitu）：`trial-recall-before/after`、`abandoned-1h/1d/3d/7d`、`winback-1d/7d/30d`——用 `{{.OfferText}}` / `{{.ValidDays}}` / `{{.PurchaseURL}}`，删「本周内有效」「最后机会」「最大优惠」。
4. 旧码 READY4U / STAYFREE / SMOOTHDAY / KEEPGOING / BACK90 / BACK85 / TRIAL80 停止下发，截止日统一改到 2026-12-05：最近收到码的人按邮件里写的期限仍能用。

6. 重建本地 MCP：`cd tools/kaitu-center && npm run build`。
7. 约 4 周后（12-01 前后）看 `recall_stats` 决定去留。
