# 内容收益统计（每篇文章带来多少钱）设计

- 日期：2026-11-10
- 状态：已批准；11-10 修订内容身份（cid → slug），见 §3.1
- 方案：A（统一编号 + 链接规范 + 汇总），David 11-10 选定

## 1. 为什么做

增长要「记录效果、按效果决定做不做」。文章是现在的主力渠道之一（站内指南 + 以后的站外文章：知乎、小红书、V2EX 等），但目前：

- 站内只能按网址看到「阅读 → 注册 → 付款」的**人数**，没有**金额**，也不包括「点下载」这一步。
- 站外文章没有统一标记，近 30 天的数据里一篇都看不到。
- 曝光（Bing）和转化（漏斗）分在两个地方，没人把它们拼到一起。

目标：**每篇内容（站内或站外）一行：曝光 → 阅读 → 点下载 → 注册 → 付款次数 → 金额**，每两周更新一次，写进增长台账，用来决定一个题材继续写还是停。

## 2. 目标 / 非目标 / 反目标

**目标**
1. 每篇内容有稳定的身份：站内 = slug（发布后不改），站外 = 平台/话题；改标题不影响统计。
2. 站外文章只要按规范放链接，就能被统计到。
3. 每篇能看到付款金额（美元）。
4. 每两周出一张表，格式固定，可以和上一期对比。

**非目标**
- 不做短链 `kaitu.io/a/<编号>`（方案 C）。等出现不允许放长链接、但又值得追踪的平台时再做。
- 不接入 Google Search Console（另立项）。
- 不追踪站外平台自己的阅读量（知乎、小红书后台数字靠人工抄进登记表，可选）。

**反目标**（技术上做成了也算失败）
- 金额算得比真实多，比如同一个人的付款被几篇文章重复计入后简单相加，当成总收入。
- 统计口径悄悄变化，导致和上一期不可比。

## 3. 设计

### 3.1 内容身份：站内用 slug，站外用「平台/话题」（11-10 修订）

> 初版用永久编号 cid。修订理由：后端记录的是进站路径，cid 要靠当前 frontmatter 反查路径，slug 一改历史照样断档，cid 并不能解决它要解决的问题；反而多出 24 篇补字段、守卫测试、报告里 `c0019` 不可读。

- **站内文章**：身份 = 进站路径 `/guides/<slug>`（`landing_path` 已去掉语言前缀，各语言版本自然合并）。**slug 发布后不改**（这也是 SEO 要求），写进 `kaitu-content` skill；万一必须改，在登记表「别名」列记下旧路径，报告合并两行。
- **站外文章**：身份 = `<平台>/<话题>`，如 `zhihu/claude-ban`。话题用小写字母、数字、连字符；对应站内文章时直接用那篇的 slug。
- **登记表** `docs/marketing/content-registry.md`：列站外文章（平台、话题、标题、地址、发布日、对应站内 slug），以及改过 slug 的站内文章的别名。站内文章不必逐篇登记（文件本身就是清单）。不加守卫测试。

### 3.2 链接规范

站外文章指向官网的链接都带：

```
utm_source=<平台>&utm_medium=article&utm_campaign=<话题>
```

- `<平台>` 取值固定：`zhihu`、`xiaohongshu`、`v2ex`、`weibo`、`wechat`、`x`、`reddit`、`other`。新增平台要同时改后端白名单。
- 站内文章不需要带标记（按进站路径统计）；已有的 `/install?utm_campaign=<slug>` 保留。
- `kaitu-content` skill 和 `kaitu-access-guides` skill 里补上这条规范。

### 3.3 后端：漏斗加金额和一条「内容转化」路径

1. **新漏斗路径 `content_conversion`**：访问（任意网页）→ **新注册**（进站之后才创建的账号；登录老账号不算）→ 付款，窗口 336 小时（14 天，与 `guide_conversion` 相同）。和 `guide_conversion` 的区别是进站页面不限于 `/guides/`，这样落在首页、`/install` 的站外流量也能统计到。`guide_conversion` 保留不动，保证历史可比。
2. **所有漏斗的分组结果都加上付款金额**：到达「付款」这一步的人，在窗口内的付款金额合计（美元，扣除退款）。只计入走完这条路径的付款，同一个人在同一个漏斗里只归给一个分组，不会重复计算。
3. 点下载这一步沿用现有的 `web_install` 漏斗，按同样的维度分组，不新造。
4. **新分组维度 `content`**：服务端为每个人算出唯一的内容键。进站记录的 `utm_source` 在平台白名单里时，取 `<utm_source>/<utm_campaign>`；否则取进站路径。这样只查**一次**，一个人只落在一行，站外文章链回站内文章时也不会两行重复计数。各行可以相加，表格可以出合计行。按这个维度分组时，组数上限提高或按前缀过滤，避免小样本指南被并进 `(other)`。

### 3.5 口径（我的决定，审阅第 2、3、5、6 条）

- **统计哪批人**：只统计**窗口已走满**的人。报告日为 T 时，取 [T−28, T−14) 进站的人，曝光也取同一时间段。转化数据因此比当天晚两周，但每一期都是完整的，和上期可比。
- **只算拉新**（David 11-10 定）：只统计进站后才注册的新用户。老用户读完文章后续费或购买不计入，因为这一轮增长的目标是拉新，老用户续费归召回那条线统计。
- **金额**：这个新用户进站后 14 天窗口内的**全部付款**（首购和续费都算），扣除截至出报告时已知的退款，单位美元。报告写进台账后就是快照，不回头重算，所以之后发生的退款不会改动历史数字。
- **多语言**：同一 slug 的各语言版本自然合并成一行（`landing_path` 本来就去掉了语言前缀）。
- **多次进站**：沿用现有逻辑，归给能走完全程的最早那次进站（首次触达）。写进第 4 节盲区。

### 3.4 汇总：skill `content-roi-report`

由 Claude 按固定流程生成，每两周一次（可以用 `/schedule` 定时）：

1. 读登记表（站外文章、别名）和 `web/content/zh-CN/guides/`（站内标题）。
2. Bing：`bing_site_pages` 取每个路径近 14 天的曝光和点击（只有站内页面有）。
3. `content_conversion`：按 `content` 分组，开推断归因。
4. `web_install`：同样两种分组，取「点下载」人数。
5. 合成一张表写进台账：

| 内容 | 标题 | 位置 | 曝光 | 阅读 / 进站 | 点下载 | 新注册 | 付款人数 | 金额 | 与上期相比 |
|---|---|---|---|---|---|---|---|---|---|

6. 表下面固定写明：统计窗口、是否含推断归因、哪些行样本太小（少于 30 次进站标「样本小」）。

## 4. 已知盲区（要写进报告）

- 读完文章直接去 App Store 下载、在 App 里注册的人，网页和 App 之间没有确定的关联，只能靠推断归因接上一部分，所以付款数**偏低**。
- 站外读者如果没点链接，而是自己搜索「开途」进站，会被算成「直接访问」或「搜索」，归不到那篇文章上。
- Bing 只是搜索流量的一部分，Google 还没接。
- 一个人如果先直接访问过官网，后来才从某篇文章点进来付款，会归给第一次访问，不会算到那篇文章上（首次触达）。

## 5. 考虑过的方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A（选定，11-10 修订为 slug 身份）** | 稳定身份 + 链接规范 + 漏斗加金额 + 汇总 skill | 后端小改动；站外靠规范自觉；金额可算 |
| B | 只做链接规范 | 零研发，但算不出金额，改 slug 会断档 |
| C | A + 内容编号做成漏斗维度 + 短链 | 最完整，覆盖不让放链接的平台；要改网站和后端，研发量最大 |
