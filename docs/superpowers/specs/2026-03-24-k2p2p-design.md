# k2p2p — NAT Traversal for Home Access

## Overview

k2p2p enables users to deploy a node at home ("home") and connect back from anywhere ("away") via peer-to-peer NAT traversal. The data plane is k2v5 — k2p2p only handles connection establishment.

## Roles

| Role | Location | Function |
|------|----------|----------|
| **home** | Fixed (e.g. China) | Deploys node, registers with API, accepts incoming connections |
| **away** | Roaming (e.g. abroad) | Queries API for home's address, initiates connection |

## Architecture

```
k2p2p = NAT traversal layer + k2v5 data plane
```

After hole punching succeeds, the resulting UDP channel carries standard k2v5 QUIC traffic (k2cc, ECH, auth, stream framing). Upper layers receive `wire.Dialer` / `wire.Listener` — indistinguishable from a direct k2v5 connection.

## NAT Traversal Strategy (Tailscale-inspired)

Three-tier approach targeting ~94% direct connection rate:

### Tier 1: Standard Hole Punch (~85% of NAT pairs)

Both sides discover public address via STUN, exchange through API server, simultaneously send UDP packets to each other. Works for all cone NAT types.

### Tier 2: Easy-Hard Asymmetric (~7%)

When one side has symmetric NAT and the other has cone NAT, the cone side's port is stable. The symmetric side sends to that stable port.

### Tier 3: Birthday Attack (~8%, hard-hard)

When both sides have symmetric NAT:
- Both open ~256 UDP sockets simultaneously
- Each side sends from all sockets to a predicted port range on the other side
- Birthday paradox gives >90% collision probability per round
- Multiple rounds push success rate higher

### Fallback: k2s Relay

When all direct attempts fail, traffic relays through the nearest k2s server via standard k2v5. The system continuously attempts to upgrade relay connections to direct.

## Signaling

Central API server (not k2s) as single source of truth:
- **home → API**: Register UDID + STUN-discovered address, periodic keep-alive
- **away → API**: Query home's address by UDID
- **API → home**: Notify "away wants to connect" with away's address (requires persistent connection: WebSocket or long-poll)

## Anti-Censorship

ECH is required — primary scenario is home deployed in China with traffic traversing Chinese networks. The QUIC connection established after hole punching uses the same ECH + TLS fingerprinting as k2v5.

## STUN Server List

Maintained curated list of public STUN servers to ensure reliable NAT discovery. List should be updatable without client release.

## Package Structure

```
k2p2p/
├── CLAUDE.md
├── stun.go          # STUN probing + NAT type classification (easy/hard)
├── punch.go         # Hole punching: standard bidirectional + birthday attack
├── signal.go        # Signaling client (API server: register/query/notify)
├── home.go          # Home: STUN → register → listen for notify → punch → QUIC accept
├── away.go          # Away: query → punch → QUIC dial → return wire.Dialer
└── k2p2p_test.go
```

## Interface Boundary

```go
// away.go — returns standard wire.Dialer after successful punch
func Dial(ctx context.Context, cfg Config) (wire.Dialer, error)

// home.go — returns standard wire.Listener after successful punch
func Listen(ctx context.Context, cfg Config) (wire.Listener, error)
```

Engine and daemon layers receive `wire.Dialer`/`wire.Listener` — no awareness of whether the connection was established via direct dial or NAT traversal.
