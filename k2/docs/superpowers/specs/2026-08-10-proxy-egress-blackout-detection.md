# 代理层出网黑洞检测 —— 交接设计说明

**日期**：2026-08-10
**状态**：设计交接稿，未实现
**范围**：k2 submodule —— `core/`（tunnel.go 计数细化）+ `engine/`（health.go 判据与动作）
**已落地的前置**：`f70b71a feat(core): report dial outcomes in the heartbeat` —— 四个 dial 计数器 + heartbeat 增量字段，纯观测、无消费者。本设计要做的就是给它加消费者。

---

## 0. 先划边界：这份文档和「双通道质量记分板」不是一回事

同日的 `2026-08-10-dual-transport-quality-scoreboard-design.md` 覆盖的是**通道选择**，本文覆盖的是**节点可用性**。两者正交，**不要合并实现**。

| | 记分板 spec | 本文 |
|---|---|---|
| 回答的问题 | 同一个节点上，走 QUIC 还是 TCP-WS | 这个节点还能不能把流量送出去 |
| 信号来源 | wire 层：echo、握手、K2CC 丢包、dial 延迟 | 代理层：dial 成功/失败结果 |
| 对 proxy-layer 错误 | **明确排除**（该 spec §6）—— 正确，换通道救不了出不了网的节点 | **正是唯一输入** |
| 唯一正确的动作 | 切换通道 | 换节点 |

记分板 spec 的 §6 那条排除规则是对的，不要去改它。本文存在的理由，恰恰是那条排除规则留下的空白：**两条通道都健康、echo 全绿、丢包 0.000、健康 FSM 判 healthy，而每一个请求都在代理层超时** —— 这个状态下记分板按设计什么都不做，健康 FSM 也什么都不做。

工单 #3463 的调查暴露了这个空白。注意 #3463 的**直接**根因（echo 超时误分类）已经在 `a3e9d34` 修掉了，那属于 wire 层。本文针对的是同一次调查中发现的**另一个**、至今无人覆盖的失败类。

---

## 1. 要覆盖的失败类

节点活着、握手通过、echo 通过（echo 在 QUIC 连接内部反射，**按设计不出节点** —— 见 `wire/quic.go` StreamTypeEcho 分支的注释），但节点自身无法到达目标：egress 网卡/路由挂了、上游被封、配额掐断、上游 DNS 死了。

客户端表现：每个 `DialTCP` 卡满 5 秒 stream 响应超时后失败。`wire/CLAUDE.md` 明确禁止在 stream 超时上触发 fallback —— **这条禁令是对的**，同一节点换 TCP-WS 没用。于是无人接手，用户看到"已连接但什么都打不开"，且永不自愈。

`#3420`（UDP mux 死缓存）是这个形状的另一个实例。

---

## 2. 判据设计：难点全在假阳性

"dialFail 很高"有三种成因，只有第一种该触发动作：

| 场景 | 该动吗 | 如何排除 |
|---|---|---|
| (a) 节点出不了网 | **是** | —— |
| (b) 用户在访问被墙/不存在的站点 | 否 | 见下"全灭判据" |
| (c) 隧道刚建立或空闲 | 否 | 最小尝试数门槛 |

**建议判据**（参数为起点，需实测调整）：

```
窗口 W        = 60s（两个 heartbeat）
最小尝试数 N  = 10        # 低于此不做任何判断
成功率        = ProxyOK / (ProxyOK + ProxyFail)
触发条件      = 连续 K=2 个窗口内，尝试数 ≥ N 且成功率 == 0
```

**为什么是"恰好等于 0"而不是"低于某阈值"**：场景 (b) 下用户总会有一部分请求成功（其它站点、DNS、后台服务），成功率会低但不为零。节点真的出不了网时是**全灭**。用"严格为 0"做判据，代价是漏掉部分性故障（比如只有某些目标不通）—— 这个取舍是刻意的：**宁可漏报，不可误报**。误报的后果是打断用户正在用的连接，而这个模块的整个存在理由就是修一个"自动机制误判导致失明"的事故，不能再引入第二个。

---

## 3. 实现前必须先做的一件事：细分失败类型

**当前 `recordDial`（`core/tunnel.go`）把所有失败一视同仁**，包括 wire 层错误。但本设计只应消费 **proxy-layer** 失败 —— wire 层失败归记分板和 re-race 管，混进来会导致两套机制对同一个故障同时动作。

`core/outbound_wire.go` 已有现成的判别式 `isProxyLayerError(err)`（它现在用于决定是否上报 `WireErrorReporter`）。实现时应把 `ProxyFail` 拆成 `ProxyFailUpstream`（proxy-layer，节点收到了请求但送不出去）和 `ProxyFailWire`（wire 层，请求没到节点）。**只有前者进本设计的判据。**

这一步是本设计的先决条件，不是可选优化。另需确认：`core/dns/proxy.go` 的 DNS 代理有自己独立的 dial 路径（`DIAG: dns-proxy-dial-fail`），不经过 `ClientTunnel.recordDial` —— 决定要不要一并计入（建议计入，DNS 全灭是这个故障最早的信号）。

---

## 4. 动作：换节点，不是换通道

现成的机制是 `reRaceChan` → `engine.outboundReplaceLoop` → 全量 `RaceTransport`（重选服务器/端口）。

**依赖关系**：记分板 spec 的 §4.2 把 re-race 的语义**收窄**为"换服务器/端口"这个正交维度，通道内切换交给 channelSelector。收窄之后 `reRaceChan` 才正好是本设计需要的动作通道。因此**本设计应排在记分板 Phase 1/2 之后实现** —— 提前做会撞上该 spec §1.1 根因 C 描述的两机制冲突。

护栏：
- 冷却 ≥ 5 分钟，指数退避（换节点是重操作，会断掉存量连接）
- 连续换 N 次（建议 3）仍不通 → 停止自动换，退回 `healthMonitor` 现有的 `HealthCritical → maybeAct → onReconnect` 兜底。连换三个节点都不行，问题就不在节点上。

---

## 5. 强烈建议：观测先行，分两步发

**第一版只加事件，不做动作**：新增 `DIAG: proxy-blackout`（判据命中时记录，字段 `window`, `attempts`, `okRate`, `consecutiveWindows`, `outbound`），跑一到两个版本，从线上工单日志里统计命中率与误报率，再决定是否开启自动换节点。

理由很直接：#3463 的教训就是"一个自动判断机制悄悄判错，导致系统完全失明"。这里要加的又是一个自动判断机制，而且动作更重（断连接）。先拿真实数据验证判据，再给它权力。

---

## 6. 测试要求

沿用记忆中的测试教训，尤其是"绿测试可能根本没跑到目标代码"与"验证工具本身要有独立判别式"：

1. **纯函数判据全覆盖**：窗口切分、最小尝试数门槛、连续窗口计数、成功率恰为 0 与恰有 1 次成功的边界。参照 `engine/health.go:echoStep` 的纯函数抽取模式（无 time/IO/log）。
2. **三种假阳性各一个测试**，且必须是**会失败的对照**而非确认性测试：
   - 全部访问被墙站点但有少量成功 → 不得触发
   - 空闲隧道（尝试数 < N）→ 不得触发
   - 刚建连的头一个窗口 → 不得触发
3. **变异验证必做**：把判据改成"成功率 < 0.1"，第一个假阳性测试必须变红。若不变红，说明测试没打到判据。
4. **已知坏的对照**：构造一个真正的全灭场景（所有 dial 返回 proxy-layer 错误），确认触发。只有"该触发的触发了 + 不该触发的没触发"两侧都验证过，判据才算立住。
5. 失败计数细分（§3）需要单独的测试：wire 层错误**不得**计入 `ProxyFailUpstream`。

---

## 7. 信心与发布

按 release confidence framework，**代码信心与业务信心分两个数打分**。本设计动的是自动重连触发条件，判错会打断用户正在使用的连接 —— 无真机 smoke 的情况下业务信心封顶 6-7。若采纳 §5 的观测先行方案，第一版（纯事件、无动作）可以按 desk-only 观测类改动评分。
