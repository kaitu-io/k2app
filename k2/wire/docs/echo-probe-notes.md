# Echo probe classification & dial evidence — full notes

Moved **verbatim** from `wire/CLAUDE.md` (2026-11-11) to keep that always-loaded file short. The invariants stay summarised in `wire/CLAUDE.md`; this file is the full rationale, incident history and the tests that pin each rule. Read it before changing the code it describes.

- `echo-probe-unsupported` backward compat: `IsEchoUnsupported(err)` returns true for all non-timeout errors (stream reset/EOF = old server, which hits `QUICServer.handleStream`'s `default:` → `stream.Close()` → client reads EOF). All three consumers share this one predicate — `race.go` (unsupported still wins the race), `probe.go` (short-circuits to `EchoSupported=false`, `Score()` sentinel `-1`), and `engine/health.go` `echoStep` (unsupported grows trust, never strikes). So a misclassification here blinds transport selection, node scoring, and re-race simultaneously. **A probe that never reached a live connection is a third class, not "unsupported"**: `QUICClient.RunEchoProbe` with no cached conn (every `Reset`/`ResetConnections` drops it until the next lazy dial) or with a conn already closed, and `TCPWSClient.RunEchoProbe` whose connect fails non-timeout, return `ErrEchoNoConnection` (`IsEchoNotProbed`; relabel only via `echoNotProbed`, which never touches a timeout). `echoStep` classifies it separately (no false `DIAG: echo-probe-unsupported`; Debug log only) but keeps the trust/strike arithmetic **identical** to unsupported (trust+1, strikes→0) on purpose — freezing trust pins the loop at 1s while unconnected (mobile wakeups) and freezing strikes carries a dead path's strikes across a network `Reset` (review 2026-11-03). `RecordEchoResult` records nothing. **"Conn already closed" is judged by quic error type, not only `conn.Context()`**: on a remote CONNECTION_CLOSE quic-go's run loop wakes blocked stream reads (`streamsMap.CloseWithError`) *before* its deferred `ctxCancel`, so the probe can see `Application error (remote)` while the context still reads alive (~1% of single probes; all three `runProbeOnce` rounds lost it ~0.1–0.2% → rollback armed onto a dead conn). `RunEchoProbe` therefore also relabels when `isQUICConnClosedErr` (Application/Transport/StatelessReset/VersionNegotiation/Idle/HandshakeTimeout errors; never `StreamError` — a pre-echo server, i.e. before echo dispatch landed in `6060c7aef` 2026-03-19, only `stream.Close()`s an unknown stream type in `handleStream`'s `default:` and never closes the connection). Pinned by `TestRunProbeOnce_ConnDiesAfterHandshake_NotArmed` (stress `-count=1000`) and `TestQUICRunEchoProbe_RealIdleTimeoutStaysFailure`. `TransportManager.runProbeOnce` (QUIC recovery during fallback) now treats it as **not OK** (`!IsEchoUnsupported` is true), so a recovery probe without a live QUIC connection no longer approves a switch back — intended, safer. **Dead node with no cached connection** (refuses / resets / auth-rejects every connection — PVE S8 2026-11-05, connected/null for 100s+) is closed by user-dial evidence, not by the probe: `dial_failure.go` — `TransportManager.DialTCP/DialUDP/DialStreamUDP` (user traffic only; `RunEchoProbe` incl. tcpws's own connect, and `runProbeOnce`, bypass them, so a probe can never manufacture its own evidence) record connect-level failures (transport errors + **coded** `ErrMetadataRejected`, i.e. carrying a `StreamError`: 401/402/403/503) into `connFail` {seq monotonic, at = newest unresolved, gen}; an answered dial (nil or a status-carrying proxy error) clears `at`, `Reset` / `ResetConnections` / `ReplacePrimary` clear it and bump `gen` (a dial straddling the clear records nothing — check and store are one step under `connFail.mu`, a leaf lock with no I/O). No opinion: caller-ctx cancel, `ErrNotConnected`, `ErrDatagramRelayUnhealthy`, unanswered response timeouts, and the **code-less** metadata reject — k2s sends that legacy `unauthorized` when it can't reach Center (`metadata_auth.go` default branch), and engine maps it to terminal 401, so counting it would turn a Center outage >15 min (cookie/auth-cache TTL) into fleet-wide disconnects (review C1). A nil "success" is not always a round trip (UDP over a cached conn) — fail-safe here (only clears), never reuse it as proof of life. Read via `ConnectFailures() ConnectFailureInfo` {Seq, First (first failure of the current unresolved run — cleared with Last), Last, Gen}; consumer is engine's `echoStepDial` (which times re-races from `First`). Tests inject the clock with `SetConnFailClock`. Before this fix it read as unsupported — Android resets the transport on the connectivity change right after VPN-up, so the false DIAG fired on ~every connect against echo-capable 0.4.14 servers.
- **A timeout is not `context.DeadlineExceeded`.** `EchoProbe` arms its response read with `stream.SetReadDeadline`, and quic-go answers an expired stream deadline with its own `deadlineError` — it unwraps to `os.ErrDeadlineExceeded` and reports `net.Error.Timeout()`, but **never** matches `context.DeadlineExceeded`. `IsEchoUnsupported` originally tested only the latter, so a black-holed data path (handshake passes, Short Header dropped — exactly what echo exists to catch) read as "old server, no echo support": trust grew, strikes stayed 0, no re-race, no TCP-WS fallback, and the UI kept showing connected while nothing loaded. Ticket #3463. Because the predicate's default is fail-open, a missed failure mode is silent — over-match timeouts here. Regression cover: `TestIsEchoUnsupported_RealStreamDeadlineIsNotUnsupported` drives a real quic-go connection to a real read deadline; every other echo test feeds a synthetic error and is blind to this class of bug.
- **A duration measured with two `time.Now()` calls is routinely 0 on Windows.** Go's monotonic clock on windows/amd64 reads `KUSER_SHARED_DATA.InterruptTime` (`runtime/time_windows_amd64.s`), which only advances on a clock interrupt — 0.5 ms on the lab VM and GitHub runners, 15.6 ms on a machine with the default timer resolution; 99.999 % of back-to-back pairs read equal there, versus a 41 ns step on macOS. So anything faster than a tick (a stubbed echo in a test, a LAN node in production) yields `rtt == 0`. `RecordEchoResult` treats a successful tcpws echo with `rtt <= 0` as a full-quality sample that leaves the min-RTT ratchet alone; before that it dropped the quality half, pinning `scoreTCPWS` at 0.5 and failing `engine`'s two `TestBackupProbe_MobilePowerSaving*` tests on every Windows CI run (2026-09-15 → 09-30). Pinned by `TestRecordEchoResult_TCPWSZeroRTTIsFullQuality`. When you write a test that asserts on a measured duration, make it pass with a zero reading or you will only find out on `test-windows`.
