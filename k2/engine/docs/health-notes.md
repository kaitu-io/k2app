# Engine health & probing notes — health FSM, echo / backup probes, wake, path memory

Moved verbatim from `engine/CLAUDE.md` (2026-11-14). **Read this before changing `health.go`, `echoProbeLoop`, `backupProbeLoop`, `suppressStrike`, `wakeDetector` or `path_memory.go`.** Wire-side counterparts: `wire/docs/echo-probe-notes.md`, `wire/docs/selector-notes.md`; heartbeat fields: `k2/docs/diag-events.md`.

- `health.go` — `healthMonitor` (1Hz sampling, ring buffer 300s, EWMA smoothing α=0.3 on smoothWireLoss via `updateSmoothLossLocked` — input is k2cc's **uplink** `PacketLossRate` only; `WireStats.DownlinkLossRate` is heartbeat-only by decision (users at 27-37% sustained downlink loss rate only good — see `wire/CLAUDE.md` `downlink_loss.go`; pinned by `TestHealthMonitor_DownlinkLossDoesNotChangeHealth`), health FSM: healthy→degraded(≥5 streak)→critical(≥5 streak), corrective action: wire reconnect). **The reconnect preserves the wire scoreboard and backs off per repeat**: `onHealthCritical` → `e.reconnect(preserveScoreboard=true)` → `wire.TransportManager.ResetConnections` (connections only; scores / selector state / flap history survive — same path, same evidence). The first reconnect of a critical episode fires immediately ("the connection went stale" is worth one redial); if the redialed connection is critical again the path itself is lossy, and repeats wait `actionCooldownBase` (30s) doubling to `actionCooldownMax` (120s) — long enough for the channel selector's quality path (2 fresh backup samples at the 5s cadence + 10s sustain) to move traffic to tcpws in between. Ten consecutive healthy samples end the episode; a network reconnect (`doNetworkReconnect` → `resetActionBackoff` + `reconnect(false)`, i.e. the wiping `Reset`) forgets it. `resetCounters` (called by every reconnect) deliberately does NOT touch the backoff. Before this (ticket #3747, Android) a lossy-but-reachable QUIC produced a 10s reconnect loop that redialed the same path and wiped the selector's evidence each time, so the user could never reach tcpws. Pinned by `TestHealthMonitor_ReconnectBackoffGrowsAndResets` / `TestEngine_HealthReconnectPreservesScoreboard_NetworkReconnectWipes`. `sample()` uses primaryTM for heartbeat stats and for `HealthSnapshot`'s `ScoreQUIC`/`ScoreTCPWS`/`ActiveChannel` fields (`json:"score_quic"/"score_tcpws"/"active_channel"`, primary outbound only — same scope as everything else in the snapshot). It also calls `WireStats()` on every OTHER outbound in `hm.tms` (side-effect only, return discarded) — `WireStats()` is the one production path that primes a `ChannelScore`'s QUIC-quality component (`wire.TransportManager.RecordQUICStats`), so without this loop every non-primary outbound's `scoreQUIC.quality` would stay permanently uninitialized and its `ScoreQUIC` would be capped at `avail×0.5`, eventually false-tripping wire's quality-path switch-away on a perfectly healthy QUIC outbound. `echoLoop`: one primary-probe goroutine (`echoProbeLoop`) AND one backup-probe goroutine (`backupProbeLoop`), independently timed, per TM.
  - `echoProbeLoop` probes via `wire.EchoProber` on an exponential-trust schedule (`echoIntervals` 1s→16s, `echoProbeTimeout` 2s); 3 consecutive real failures trigger per-TM re-race, so wire death is detected in ~5s. **`reRaceFailStreak` decays on recovery** (review A): `healthMonitor.targetRecovered` (← `wireHealthRecovered`) resets it when the probe sees the node answer again — an echo OK, or a failure run ending without a Reset in between (an answered user dial) — so separate outages in one session never add up to Phase B. **Not-probed (`wire.ErrEchoNoConnection`) strikes only on user-dial evidence** (`echoStepDial` / `readDialFailEvidence`): dials are *failing* iff `tm.ConnectFailures()` has an unresolved failure (no later answered dial, no Reset/ResetConnections/ReplacePrimary) < `echoDialFailWindow` (30s) old AND the engine's network is up (`hm.netUp` ← `netCoordinator.isNetworkUp`, wired by `wireHealthNetUp`; mobile no-network → no strike, no new replace-loop work; desktop never reports down). While failing (S9 ruling 2026-11-05): for the first `echoDialFailFastFor` (**60s**) of the run the probe is pinned to `echoIntervals[echoDialFailTrust]` = **2s**, then back to the not-probed backoff (review C: manual mode on a dead node with a background app retrying is bounded; `TestDeadNodeTimeline_ManualModeDeadNodeBounded`); `DIAG: echo-probe-fail` for this class is Warn once per run, Debug after; a run's end zeroes dial-failure strikes (frozen quiet-tick strikes never leak into the echo path, review D — echo strikes from a cached connection are kept) and counts as recovery only on the not-probed path (review 3 M-1: over a cached connection an "answered" dial can be a UDP open that sent nothing); a Phase-B swap (new `ot.tm`) restarts the seq/gen/run bookkeeping and zeroes strikes (review E / 3 M-2); a tick preceded by a *fresh* failure (seq moved) is a strike, a quiet failing tick keeps the count (failures arrive in bursts); a re-race needs 3 strikes **and** the run (since `ConnectFailureInfo.First`) to have lasted `dialFailReraceAfter(k)` = 8s / 24s / +16s for the k-th re-race of that run (`echoLoopState.dfRunFirst/dfReraces`; a new run restarts k). That gate is what pins both bounds wherever the probe timer was: dead node → Phase B 29–31s after the first failing dial at ≥1 failure/2s (worst 37s at 1/3s; target 45s for `DIAG: outbound-failover`), and a 20s refusal never gets a second failed Phase-A (the first answered dial ends the run before 24s) → no Phase B — `echo_dialfail_timeline_test.go` drives both on a fake clock (`hm.clock` + `tm.SetConnFailClock`). Not failing → `echoStep`'s not-probed arithmetic unchanged (idle/offline cadence ramps to 16s as before). When the connection generation moved since the last probe a not-probed probe first zeroes strikes (gen is read **before** `RunEchoProbe`, so a Reset during a probe is seen at the next one), so old-path strikes never combine with a new-path failure. Caveat: a TCP-WS primary's not-probed probe re-connects, so the 2s cadence adds refused connects while (and only while) user dials are failing. One failure strikes at most once; idle = no dials = no strikes. This is what lets a node that refuses/402s every connection reach `outboundReplaceLoop` (and Plan A's 401/402 fail — the race error carries the code). A successful Phase-A (`phaseA`) also `ClearWireError()`s a stale non-user-action wire error (the connected+503 window after a hold). An `init()` guard panics if that worst case ever reaches QUIC `MaxIdleTimeout` — past that point the loop adds nothing over quic-go's own idle timer. **Backward compat**: `echoStep` routes `wire.IsEchoUnsupported` errors (pre-echo servers) to trust-growth rather than strikes, so old servers never storm re-races. That predicate is fail-open, and misreading a real timeout as "unsupported" is what silently disabled re-race entirely in ticket #3463 — see the timeout note in `wire/CLAUDE.md` before touching it. Each probe also feeds the dual-channel quality scoreboard: `RecordEchoResult(primaryChannel, ...)` + `EvaluateSelector(now)` (see `wire/CLAUDE.md` transport.go for the FSM this drives) — a second, uncoupled job on the same probe, never influencing trust/strikes.
    - **Strike gating (`suppressStrike`)**: scoring is never gated, but two topologies keep an echo failure OUT of the strike counter **while the TCP-WS channel has live proof of life**, because there a failing echo is expected rather than informative. (1) Fallback active (`ActiveChannel()=="tcpws"`) while the primary is still the QUIC dialer, AND `TCPWSChannelRecentlyHealthy(30s)`: that QUIC path is known dead — leaving it ungated, its timeouts strike 3× in seconds and fire a re-race that closes the QUIC dialer with no backup and `ReplacePrimary(tcpws)`es over the selector's whole fallback state, so the user never returns to QUIC; recovery of that path is owned by wire's `runProbeOnce`. (2) The primary IS the tcpws channel and `TCPRecentlyHealthy(30s)` is true: `TCPWSClient` became an `EchoProber` in this branch, so tcpws primaries now run the 1-16s schedule with a 2s timeout, and TCP head-of-line blocking under bulk transfer can blow that 2s three times in a row on a session that is working — the re-race would close the very session serving the transfer. With no recent TCP success, strikes accumulate normally in **both** topologies.
    - **Why case (1)'s proof condition is mandatory, and the trade it accepts**: `probeOnce` is the ONLY producer on `reRaceChan`, Phase B server replacement (`replaceOutboundServer`) is reachable only through it, and `assess()` cannot reach critical on TCP-WS stats — so there is no other automated escalation. Suppressing on topology alone would sever it exactly when the NODE dies while a user sits in fallback (crash, quota cutoff — routine fleet events), leaving both channels dead and the user hung until a network change or manual reconnect. Accepted trade: an **idle** fallback user produces no dials, so has no live proof, so strikes resume and a re-race may land tcpws as primary — which is now a stable, honest terminal state (the C1 topology gates stop the FSM and the recovery probe from fabricating a QUIC channel there). The idle case is thus the pre-fix status quo minus the phantom loop. Note the proof clock is fed by **`DialTCP` only** (wire's `recordTCPWSDialSuccess`): that path reads a server response, so success is end-to-end; UDP dials over tcpws open a smux stream with no round trip and keep "succeeding" against a dead node, which would manufacture exactly the proof this gate must not have.
    - **Honest scope of root cause C**: the spec claimed channel switching would leave re-race entirely. What is delivered is narrower — re-race no longer fires *from the dead primary during fallback* or *from a loaded-but-working tcpws primary*; it remains the escalation for every other echo-death, which is its intended "this outbound is beyond channel choice" role.
  - `backupProbeLoop` opportunistically echo-probes the currently-inactive channel on its own timer (never piggy-backed on `echoProbeLoop`'s tick, which would distort its re-race timing invariant). Scope is asymmetric: active=="quic" → probes tcpws at `backupProbeIntervalHealthy` (60s), upgraded to `backupProbeIntervalDegraded` (5s) once `ScoreQUIC` drops below `echoBackupProbeThreshold` (0.7, mirrors wire's private `qualityDegradeThreshold`) so the quality path's `backupFresh` gate has fresh samples by the time it needs them; active=="tcpws" → no-op, because QUIC recovery probing during fallback is already owned by wire's `runProbeOnce` (see `wire/CLAUDE.md`). `hm.mobilePowerSaving` (desktop `false`, set from `Config.MobilePowerSaving`) narrows this to **distressed only** (`primaryDistressed`: the health FSM in `critical`, which only smoothed loss > 0.25 can reach, **or** `wire.TransportManager.DataPathDistressed` — three consecutive quic `DialTCP`s sent and never answered): while QUIC is healthy or merely degraded *and answering requests*, mobile probes nothing and relies on protocol keepalive; once distressed it probes at the 5s cadence until the selector switches or QUIC recovers. The second key (round 3, #3757) closes the loss gate's blind band: CC loss only moves when a monitor interval completes, so an app-limited sender reports `loss=0.000` for minutes while every request dies at the 5s deadline, and the loss-only gate never opened (#3757: 205/260 QUIC heartbeats at loss 0; the emulated per-flow-policed link took 32s of dead dials to cross 0.25). Desktop is not gated but its cadence upgrade was score-only; distress now upgrades it to 5s as well, since the selector's data-path fast path needs two fresh tcpws samples and the 60s cadence would take a minute to supply them. Health grading itself is untouched — distress opens probing, `wire`'s selector decides. Pinned by `TestBackupProbe_MobilePowerSavingProbesWhenDataPathDistressed` / `TestBackupProbe_DesktopCadenceUpgradesOnDataPathDistress`. **The gate's early returns are a WAKE cadence, not a probe cadence**: all three (`mobilePowerSaving && !critical`, `active != quic`, tcpws-primary) return `backupProbeIntervalDegraded` (5s) — pure in-memory checks, no radio — because that return value is `backupProbeLoop`'s only wake source; the original #3747 fix returned the 60s healthy interval there, so the gate opening (and a rollback to quic) was noticed up to 60s late, and since the first critical's reconnect closes the gate again for ~7s via `resetCounters`, a wake landing in that gap slept another 60s. The backup echo runs under its own `backupEchoProbeTimeout` (5s, not the primary's 2s `echoProbeTimeout`): the backup tcpws is usually cold (every health-critical `ResetConnections` drops its session too) and a cold TCP+TLS+WS+smux+metadata dial from cellular does not fit in 2s — a spurious timeout here is not a strike but a false availability sample that drags `scoreTCPWS` under `minSwitchTargetScore` exactly when the switch needs it. It is keyed on the health grade, **not** on `ScoreQUIC < 0.7`, on purpose: the score carries an RTT term, and cellular bufferbloat under a healthy download drives it to ~0.5 while a tcpws first measured under that same load gets a loaded min-RTT baseline (ratio ≈ 1.0) — score-gating would switch a healthy download onto tcpws. Loss separates "the UDP path drops bulk" (ticket #3747: carrier UDP QoS, handshake and echoes pass, nothing loads, tcpws — which the DNS control plane was already using — never got a sample) from "the shared queue is full". Pinned by `TestBackupProbe_MobilePowerSavingProbesWhenLossCritical`.
  - TCP health gate: `TCPRecentlyHealthy()` (30s window) suppresses reconnect when TCP streams are working — and, as of the final review, the echo strike above. It answers for whichever primary is installed: `*QUICClient`'s own `lastTCPSuccessAt`, or (tcpws-as-primary) the TCP-success clock `wire.TransportManager` records on `DialTCP`'s tcpws success paths. It returned a flat `false` for every tcpws primary before that second branch existed, which would have made the strike gate a silent no-op in exactly the topology it targets. Wire-layer metrics only — relay metrics are observability (see `wire/VOCABULARY.md`). `wakeDetector` (embedded in healthMonitor): detects sleep/wake via wall-clock gap, `DIAG: wake` at >5s, triggers `doWakeReconnect()` at ≥30s (aligned with QUIC MaxIdleTimeout) — the **scoreboard-preserving** reconnect (`reconnect(true)` → `ResetConnections`, backoff kept), because a wake says the connections are stale, not that the path changed; a path change arrives separately as a NetEvent / sing-tun interface change and goes through `doNetworkReconnect()` (`Reset`, backoff forgotten). `Pause()`/`Wake()` preserve the scoreboard the same way (iOS calls them on every screen lock/unlock). Before this every phone pickup on a lossy-but-reachable QUIC put the user back on it and replayed the whole escape. Pinned by `TestEngine_PauseWakeAndWakeReconnectPreserveScoreboard`. Heartbeat includes memory metrics (`heapMB`, `sysMB`, `goroutines`) via `runtime.ReadMemStats` every 30s for iOS NE jetsam diagnosis, plus `activeChannel`/`scoreQuic`/`scoreTcpws` (Task 8) so the dual-channel scoreboard is visible without DEBUG — see the heartbeat field list in `k2/docs/diag-events.md`. It also carries the **uplink** CC window since the previous heartbeat (`ccMis ccAppLimited ccFloor ccLossP90 ccRttP90 ccBwEst ccBgLoss ccMode`, via `ws.CC.Sub(hm.lastCC)`; the `SenderID` epoch restarts the window on reconnect, and tcpws fallback reads as all-zero with `fallback=true`) — `ccAppLimited ≈ ccMis` is the normal shape for a VPN client that barely uploads, not a fault; the server's `DIAG: cc-summary` is where download-direction CC lives.

- `path_memory.go` — process-scoped carry-over of the channel selector's verdict on the QUIC path (`wire.PathVerdict`): recorded from the primary outbound at `Stop`, applied to every outbound after the race in `Start`, cleared by a network-change reconnect (`reconnect(false)`), 10 min TTL because a network change while disconnected raises no event — counted from `PathVerdict.EvidenceAt` (the last quality/data-path switch-away any session observed), never from the Stop that saved it: a session that only inherited the verdict cannot renew it. One-file disk copy (`path-memory.json` beside the rule cache dir: three numbers + a timestamp) so the verdict survives the iOS extension exiting with the tunnel and Android killing the app process; `bind` adopts it only when the process holds none, `clear`/proven remove it. Package-level state — tests use `resetPathMemoryForTest`. The Stop / network-change hooks are mutation-pinned by `TestEngine_StopRecordsPathMemory` and `TestEngine_NetworkChangeClearsPathMemory_HealthReconnectKeepsIt`; the Start hook only by `test/netem/nslab.sh RECONNECT_AT`.
- `health.go` `noteActiveChannelLocked` — a change of serving channel restarts the health grade (EWMA + streaks). Without it a clean tcpws is graded critical on QUIC's loss history for a few samples and `maybeAct` reconnects the channel that just took over (ticket #4055).
